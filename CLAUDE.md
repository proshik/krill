## 1. What Krill is + status

Krill is a minimal self-hosted PaaS written in Go (`github.com/proshik/krill`) — a lightweight Dokploy alternative aimed at a ~20–50 MB control plane (vs Dokploy's ~760 MB) so the author can host a webhook Telegram bot on a 2 vCPU / 1.9 GB VPS. It deploys containerized apps and managed databases on a single-node Docker Swarm, routes traffic via Traefik, and exposes a web control plane (templ + HTMX + Tailwind v4) with a multi-tenant org → project → environment → app/db hierarchy and bcrypt/cookie auth.

Status: Phases 0, 1, 2, 2.5, 3, **4, 5** are DONE (login, image apps, Swarm services, Traefik routing, live logs, rolling updates, Dockerfile build+deploy, deploy history, UI design system + i18n, managed Postgres/Redis with volumes and external ports, multi/custom domains per app + per-domain Let's Encrypt HTTPS, **Postgres backups to S3/MinIO with cron + retention + restore**). **Phase 7 (realtime/ops)** is DONE except email/Slack: Telegram notifications, web terminal, host monitoring, and the structured log viewer all shipped. Tech-debt backlog for Phases 1–3 is fully closed. **Per-organization networks:** every organization now gets its own Docker overlay network, `krill-org-<id>` (`internal/orgnet.Name`), instead of sharing the single `KRILL_NETWORK`. `organizations.network_name` (migration 000042) records it once created; `organizations.network_migrated_at` (migration 000043) records that every one of the organization's services has actually been moved there — `network_name` alone can't carry that, since it is written *before* anything moves. `internal/deploy` (`GetOrganizationNetworkByApp`) and `internal/dbservice` (`GetOrgNetwork`) resolve an app's/instance's org network at deploy time and fall back to `KRILL_NETWORK` when it is still empty. Traefik joins every organization's network plus the base one (`traefik.Reconcile`, replacing the old one-shot `Bootstrap`; idempotent via a spec-fingerprint label so an unchanged spec doesn't force a task recreation on every restart) and is kept in sync as organizations are created (`Server.reconcileGateway`, a `func()`-typed field set by `SetGatewayReconcile` and triggered from `createOrg`, debounced 3s + rate-limited to one reconcile/minute so a burst of org creation can't be used to blip ingress repeatedly). On an existing install, `internal/orgnet.Migrator` runs once in the background **after** the HTTP listener is up (never blocks boot — a full pass can take minutes) and only once Traefik's own reconcile has succeeded (migrating services into networks the gateway never joined would be worse than not migrating): it moves each organization's databases before its apps (an app landing on the new network before its database can't resolve it by name), waits for each batch of databases to actually come up before enqueuing the apps that depend on them (a transient `ServiceStates` error is logged and polled past, not fatal), skips apps that are stopped or were never deployed, and **parks** stopped database instances instead of redeploying them (`orgnet.RunningInstancesFilter` + `dbservice.ParkInstance`: the service is rewritten onto the org network at its current replica count — zero for a stopped one — without starting it or waiting on it; skipping it would not do, because `StartInstance` only scales the existing service and would bring it back up on the shared network), and marks an organization migrated only once every step of its pass has completed — including every app deployment it submitted reaching a terminal status other than `error` (`RedeployApp` returns the deployment id and the migrator polls `ListDeploymentStatuses`; a submitted deploy proves nothing, and one that fails leaves that app on the old network). A partial pass (a failed database listing, a redeploy that errors, an app deployment that fails or is still unfinished when the 30-minute pass deadline expires) leaves the organization unmarked and the *whole* pass is retried on the next boot, not resumed piecemeal. Moving a service is an ordinary redeploy (`Deployer.EnqueueSystem`, bypassing both the per-app and per-org in-flight caps so the migration itself is never rate-limited by them), so a Dockerfile app is rebuilt (from cache, not `--no-cache`) to move networks — the first start after upgrading an install with several such apps is correspondingly slow. `docker.Engine.NetworkRemove` exists (idempotent, modeled on `NetworkEnsure`) but has no production caller yet — there is no "delete organization" endpoint in the codebase for it to clean up after.

**Panel domain:** the UI is a host process, so the swarm provider (labels) cannot route to it; instead Traefik's **HTTP provider** polls Krill at `GET /_krill/gateway/config` (`panel.ProviderPath`) for the UI's routes (`panel.DynamicConfig`: `krill-panel-https` on websecure with `tls.certResolver=le`, `krill-panel-http` redirect-only on web, service → `http://KRILL_ADVERTISE_ADDR:<listen port>` from `panel.Upstream`; routers carry priority 1 000 000 so a tenant app claiming the same host can't tie; with an IP allowlist a higher-priority `krill-panel-machine` router keeps `/webhooks/`, `/api/`, `/mcp` unfiltered). Chosen over a file provider (a bind mount ties Traefik to a host path and breaks on Colima) and over running Krill as a Swarm service (changes the install model) — same dynamic-config shape Dokploy/Coolify write to files. Singleton table `panel_gateway` (migration 000045) holds a random `secret` (`secret.Enc`, created by `panel.EnsureSecret` at startup, replaced if undecryptable) from which **two** HMAC tokens derive (`panel.DeriveTokens`): the *provider* token goes into Traefik's args (`--providers.http.headers.X-Krill-Gateway-Provider=…`; args depend only on config + secret, so the spec fingerprint is stable and `traefik.Reconcile`/`TraefikSpec` take a `PanelProvider` — zero value = provider omitted when `panel.Upstream` fails, e.g. no advertise addr or loopback listen), and the *forwarded* token is stamped by a `headers.customRequestHeaders` middleware on every proxied request (`X-Krill-Gateway`). They must differ — the forwarded token rides on every request through the domain, and `gatewayConfig` 404s any request carrying it. A valid forwarded token is how the server recognizes a gateway request (`Server.viaGateway`/`secureViaGateway` + Traefik's own `X-Forwarded-Proto`, which Traefik strips from untrusted clients): it makes `X-Forwarded-For` trusted for the login limiter (`trustForwardedFor`, per request — `KRILL_TRUST_PROXY` stays for external proxies) and cookies `Secure` (`cookieSecure(r)`; `setFlash`/`setFlashPw`/`setFlashToken` now take `r`), so direct `http://ip:8080` keeps plain cookies and remains the way back. The login page warns when `KRILL_COOKIE_SECURE=true` meets plain HTTP. State `off → pending → active`: saving a host routes it immediately but changes nothing for the direct address; `confirmPanelDomain` accepts only a request on the domain over HTTPS (`onPanelDomain`) **and** a trusted cert (`panel.CheckCertificate` dials `ADVERTISE:443` with SNI — checks the cert only, not reachability; skipped with `KRILL_ACME_STAGING`). **Direct port close** (`closePanelDirectPort`, requires active + on-domain + lockdown already on) rebuilds the control-plane ruleset with `controlPlaneServicePorts(listen, closeDirect=true)` → UI port moves from the public set to `iifname "docker_gwbridge"` (`firewall.BuildManagerRuleset(ips, public, gateway)`), applied via `lockdownControlPlane` with the dead-man switch; `direct_port_close_pending` until `confirmPanelDirectPort` arrives through the domain. `lockdownControlPlane` now drops idle keep-alive conns after Apply (`SetIdleConnCloser` → `srv.SetKeepAlivesEnabled(false/true)`) so a pre-apply connection can't carry the confirmation. Coupling with the Firewall page: a lockdown honors `direct_port_closed` and is refused off-domain when it is set; the firewall confirm also finalizes a pending panel close; **Open cluster** resets the flags; the page clears a close whose switch fired. Guards: the domain can't be changed/removed while direct access is closed or closing; apps can't take the panel host (`hostReservedByPanel` in `createApp`/`addDomain`) nor the panel an app's host; an operator on the domain can't save an allowlist excluding their own IP. **HSTS** (migration 000046, `panel_gateway.hsts_max_age`, CHECK: non-zero only while `active`; reset by `SetPanelDomainPending`/`DisablePanelDomain`): the global `panelHSTS` middleware sets `Strict-Transport-Security: max-age=N` only when `secureViaGateway(r)` AND state active AND `RequestHost(r)==host` — `max-age=0` while off, to unwind an earlier policy; never `includeSubDomains`/`preload` (the panel shares a parent domain with unrelated hosts); max-age is limited to `panel.HSTSPresets` (0/5m/1d/1w/30d/1y), set via `setPanelHSTS` (refused unless active). `TestPanelCookiesSecureOnlyViaGateway` pins the per-request Secure decision for both session and flash cookies (direct, direct claiming https, gateway https, gateway http, forged token). `Server.baseURL` prefers `KRILL_PUBLIC_URL`, then `https://<active panel host>`. No basic-auth option (it would eat the `Authorization: Bearer` of API/MCP). Rollback runbook (SSH: `nft delete table inet krill` + `UPDATE panel_gateway …`) lives in `docs/guides/domains.md`. Handlers: `internal/server/panel_handlers.go`, instance-admin routes under `/orgs/{id}/panel-domain`.

**Self-update:** an instance admin installs a newer Krill release from **Settings → Updates** without touching the host. `internal/buildinfo.Version` (linker-stamped by `release.yml` and by `make build`'s `git describe`) is what `buildinfo.IsRelease`/`selfupdate.Newer` compare against a `selfupdate.Checker`, which discovers the latest tag via GitHub's unauthenticated `releases/latest` redirect (no API, no rate limit) on a timer (`KRILL_UPDATE_CHECK_INTERVAL`) and on demand, throttled to once a minute. `selfupdate.Updater.Start` downloads and sha256-verifies that release's `krill-linux-<arch>` binary against its own `checksums.txt`, smoke-tests it with `--version` and an empty environment, keeps the running binary as `<bin>.prev` (a hard link, so there is never a moment with no binary at all), writes a `10-krill-update.conf` drop-in (`StartLimitIntervalSec=0`, so a crash-looping new binary keeps restarting instead of landing in `failed`), arms a 10-minute `krill-update-revert` transient timer, and asks systemd to restart the unit from a separate `krill-update-restart` transient unit — never `systemctl restart` directly, which would run inside `krill.service`'s own cgroup and be SIGTERMed by the very stop it requested. Coordination between the old and new process runs through marker files in `/run` (`krill-update-pending`/`-reverted`/`-rolledback`, cleared on reboot along with the transient timers they coordinate with): `Updater.ConfirmStartup`, called once the new process is serving, finds the pending marker, deletes it and cancels the revert timer — which is why a broken new binary that never gets that far is put back automatically. `server.StartupGate` answers a 503 "Krill is starting" page on the listener from the moment it opens (before migrations even run) until the router is swapped in, so the browser — and the Updates page's own poll — sees progress across the restart instead of a refused connection. `internal/server/update_handlers.go` + `templates/updates.templ` render the page and the install/rollback/status endpoints (`RequireInstanceAdmin`); `cmd/krill/selfupdate.go`'s `updateBusy` refuses to restart while a deploy, a backup/restore or a DB-instance node move is in flight — asked when the request arrives and again by the job itself right before it changes anything on the host (after the download and smoke test; before the swap for a rollback), failing the job with a `*selfupdate.BusyError` if work started meanwhile. `Previous`/`Rollback` only offer a `<bin>.prev` whose version is a release strictly older than the running one, and `install.sh` deletes `krill.prev` whenever it installs a binary, since an old one may be several releases behind. Offered only to a release build (`buildinfo.IsRelease`) — a `git describe` build from source is a semver prerelease and never "newer" than anything. The whole mechanism only works because migrations stay additive across a release (§4's compatibility policy, checked by squawk via `make lint-migrations` in CI and read by reviewers): a binary rolled back after a failed update must still be able to start against whatever schema the newer one already applied, which `database.RunMigrations` allows by skipping `Up()` (with a warning) when the recorded version is ahead of what it embeds.

**Credential host binding:** Git and registry credentials are checked against the host they were created for before Krill will use them. `internal/builder.HostOf`/`NormalizeHost` and `internal/docker.RegistryHost`/`ImageHost` normalize the credential's stored host and the app's `git_url`/`image` host for comparison; `internal/deploy/store.go`'s `checkGitCredentialHost`/`checkRegistryHost` run inside `GetApplication`, before the deployer ever reaches a clone or a pull, and fail closed — including when the stored host itself normalizes to empty, which used to bypass the check entirely. `createGitCredential`/`createRegistry` also refuse to store a credential whose own host doesn't normalize to something usable, closing the same gap at the source. A Dockerfile app's `git_url` additionally goes through the existing SSRF egress guard (`internal/netguard.CheckHost`, gated by `KRILL_ALLOW_PRIVATE_EGRESS`) before the clone starts — the same treatment S3 and registry URLs already had.

**Password changes:** any authenticated user can change their own password from the "Change password" link in the sidebar of every organization page, which opens `/orgs/{id}/account/password` inside the normal layout (`internal/auth.Service.ChangePassword`: verifies the current password, enforces a 10-rune minimum, hashes and stores the new one, and revokes every *other* session for that account so a password change actually locks out anyone else who had a live session). `users.must_change_password` (migration 000041) is set on a user the first time they're added to any organization (`createMember`, new accounts only — never on an existing user added to a second org; written by the same `CreateInvitedUser` INSERT that creates the account, so an invite can never succeed without it) and gates every authenticated route except the standalone `/account/password` form (the `Bare` layout, no navigation — a non-forced user landing there is redirected to the in-layout page of their first organization) via the `requirePasswordChange` middleware, which fails **closed**: a lookup error holds the user on the form rather than letting a transient DB blip through to the rest of the app.

**Resource defaults & build caps:** apps and DB instances with no explicit memory/CPU limit of their own now fall back to an instance-wide default — `KRILL_DEFAULT_MEMORY_LIMIT`/`KRILL_DEFAULT_CPU_LIMIT`, applied in `Deployer.withResourceDefaults` and `dbservice.Service.instanceSpec` only where the app/instance's own value is `0`, so an explicit per-resource value always wins and an unlimited container can no longer take the whole host by default. `KRILL_MAX_BUILDS_PER_ORG` caps how many deploys one organization may have in flight on the shared single-worker build queue at once, on top of the pre-existing per-app "one deploy in flight" check (`CountRunningDeploymentsByOrg`, checked in `Deployer.enqueue`; `<= 0` disables it, a query error fails closed and refuses the deploy). `internal/builder.StartCachePrune` runs `docker builder prune --force --reserved-space <KRILL_BUILD_CACHE_LIMIT>` on a `KRILL_BUILD_PRUNE_INTERVAL` ticker (Docker CLI 28+ renamed `--keep-storage` to `--reserved-space`; an older CLI that rejects the new flag gets `--keep-storage`, remembered after the first attempt) — nothing else ever trimmed the BuildKit cache, so a small VPS could otherwise fill its disk silently until builds start failing. There is deliberately no per-build network or resource isolation: BuildKit rejects a `--network` override outright and silently ignores `--memory`/`--cpu-quota`, so the queue cap and the cache prune are the only mitigations on the build side; the actual isolation for `krill-postgres` is the installer's `krill-state` network (see §10).

**Registries (private image pull):** org-scoped `registries` table (registry_url/username/password, plaintext) + nullable `applications.registry_id`. `docker.EncodeRegistryAuth(user,pass,url)` → `ServiceSpec.RegistryAuth` → `EncodedRegistryAuth` on `ServiceCreate/Update` (Swarm `--with-registry-auth`); the deployer's store loads+encodes the app's registry. `Engine.RegistryCheck` validates creds on create (engine-gated, so nil-engine tests skip it). UI: org Registries page (admin) + a registry select on app create/General. Real private pull verified on a host.

**Backups/S3 (Phase 4):** `destinations` (org-scoped S3 config: endpoint/bucket/region/keys, plaintext) + `backups` (per-logical-database, `logical_database_id` FK: cron schedule, retention N, prefix, enabled, last_run/status — see **DB instances** below for the model). Dump path = `Engine.Exec` runs `pg_dump --clean --if-exists` inside the instance's container → gzip stream → S3 (aws-sdk-go-v2, path-style for MinIO) at `<prefix>/<app_name>/<db_name>/<ts>.sql.gz`; retention keeps newest N (count-based) per logical-database directory. Restore streams S3 → gunzip → `psql`. In-process `robfig/cron/v3` scheduler (`Scheduler.Reload` after any backup mutation, wired in main + via `Server.SetBackups`). `internal/backup` (s3.go/service.go/store.go/scheduler.go); destinations org-scoped + backups chain-checked (IDOR tests). S3 tested against a MinIO testcontainer (`testutil.NewMinio`); the live `pg_dump`/restore exec path is verified on a real host (no Swarm in unit tests). `runBackupNow`/`restoreBackup` run async on a detached context. **UX simplification (2026-07-05):** the backup form now offers schedule **presets** (`backup.CronForPreset`/`SchedulePreset` — Off/Hourly/Daily/Weekly/Monthly/Custom) instead of a raw cron field; Off = empty schedule, which `Scheduler.Reload` skips registering (on-demand only — "Backup now" still works), friendlier labels ("Storage" for destination, "Keep last N backups" for retention, the S3 prefix under an "Advanced" disclosure, a state-aware Pause/Resume toggle), and an inline storage-creation form in the empty state (`createDestination` supports a `return` redirect back to the originating page). Engine unchanged — same S3 transport, same cron/retention semantics; DB and volume backups share the same form/terminology. See `docs/superpowers/specs/2026-07-05-krill-backup-ux-simplification-design.md` / `docs/superpowers/plans/2026-07-05-krill-backup-ux-simplification.md`. See [`ROADMAP.md`](./ROADMAP.md) and `docs/superpowers/` for the full trail.

**Advanced container settings:** nullable `applications` columns `memory_limit`/`cpu_limit`/`replicas`/`restart_condition`/`restart_max_attempts`/`healthcheck_*`; human units (`256m`/`0.5`/`30s`) parsed by `docker.ParseMemoryBytes`/`ParseNanoCPUs` → `ServiceSpec` `Resources.Limits` + `RestartPolicy` + `Healthcheck` in `buildSwarmSpec`; carried from the store into the deploy spec. UI: app "Advanced" tab (no reservations/placement/raw-JSON yet).

**App lifecycle controls:** Deploy/Reload/Rebuild/Stop buttons on the app General tab. Reload = `engine.ServiceRestart` (no rebuild); Rebuild = `EnqueueRebuild` (`docker build --no-cache`); Stop = `ServiceScale → 0`; Deploy brings it back up.

**Gateway route exposure:** per-domain `domains.exposed` + `domains.paths`. `traefik.AppLabels` skips non-exposed domains — **zero exposed → `traefik.enable=false` (overlay-only, internal)**; exposed + paths → `Host(...) && (PathPrefix(...) || …)` rule (anything else 404); `validPaths` guards against rule injection. **New apps are internal by default** (auto primary domain `exposed=false`, with a "not exposed" warning banner); existing domains were backfilled `exposed=true`. UI: Domains tab has a per-domain Exposed toggle + paths editor. The "who" axis (basic-auth / IP-allowlist) is done — see **Route protection** below.

**Route protection (basic-auth / IP-allowlist):** per-domain `domains.basic_auth_users` (htpasswd `user:bcrypthash`, newline-separated) + `domains.allowed_ips` (CIDR/IP, newline-separated; migration 000020). `traefik.AppLabels` attaches middlewares to the serving router (non-TLS `base`, TLS `base+"s"`; the redirect router is left unprotected) in order `ipallowlist.sourcerange` then `basicauth.users` — chained = AND. Admin-gated handlers (`addDomainBasicAuthUser`/`deleteDomainBasicAuthUser`/`setDomainAllowedIPs`) validate username-regex + `net.ParseCIDR`/`ParseIP` (canonicalized), bcrypt via `auth.HashPassword`; passwords/hashes are never logged or shown — logins only. UI: "Access protection" section on the Domains tab (exposed domains only). IDOR/admin-gate tests + a 4-lens adversarial review are green.

**App volumes/mounts + backup/restore:** `app_volumes` table (migration 000018) + a Volumes tab (admin); the deployer carries `Mounts` into `buildSpec` (fixes drift mount-loss on redeploy) and volumes are cleaned up on app/env/project delete. `docker.VolumeArchive`/`VolumeRestore` run a pinned-digest busybox sidecar (root, no network, ro archive) to tar a named volume → `volume_backups` + `internal/volume.VolumeService` (backup→gzip→S3 with count retention; restore quiesces the app first). A second `backup.Scheduler` drives cron; handlers are admin-gated with IDOR + cross-org destination checks. The live archive/restore path is verified on a real host (backup+restore round-trip of prod Readeck → MinIO).

**DB→app linking:** `app_db_links` table (migration 000019, rewired onto real FKs by 000029) links an app to a database → injects the live internal connection string into a chosen env var on **every** deploy (`internal/deploy/store.go` `resolveDBLinkURL`; overrides `env_text`; the password is pulled live via `secret.Dec`, never stored in `env_text`). Two kinds, chosen via the form's `db_ref=pg:<id>` / `db_ref=redis:<id>`: a **postgres** link points at a `logical_databases` row and is scoped to the app's own environment (`ld.EnvironmentID != c.Env.ID` → 404); a **redis** link points at a `db_instances` row directly (redis has no logical sub-resource) and is org-wide — any redis instance in the org can be linked, not just ones in the app's environment. UI: "Linked databases" section on the Environment tab (admin); links are cleaned up when the DB is deleted; IDOR/cross-org guard.

**Raw TCP/UDP published ports:** `app_ports` table (migration 000025: `host_port`/`container_port`/`protocol`, `UNIQUE(host_port, protocol)`) → `deploy.App.Ports` → `spec.Ports` (host publish mode; the `internal/docker` layer already supported TCP/UDP via `PortSpec.UDP`). Admin-gated `addAppPort`/`deleteAppPort` validate range 1..65535 + protocol ∈ {tcp,udp} and conflict-check the host port against both `app_ports` AND managed-DB `external_port` (for TCP); tenant chain-check + IDOR. UI: "Published ports" on the Advanced tab. Applied on the next deploy. Deferred: ingress (swarm LB) mode, port ranges, auto-pick, firewall/UFW.

**Build secrets/args + private git:** org-scoped `git_credentials` (PAT, token `secret.Enc`; migration 000021) + nullable `applications.git_credential_id`; private HTTPS clone authenticates via a `GIT_ASKPASS` helper (`builder.gitAuthSetup`) — the token is fed to git through env vars, never embedded in the clone URL/argv or written to the member-visible build log (`sanitizeGitURL` also strips any credentials before echoing). `applications.build_args` (non-secret → `--build-arg`) + `build_secrets` (`secret.Enc` → BuildKit `--secret` via `0600` temp files outside the build context, `DOCKER_BUILDKIT=1`, defer cleanup). Dockerfile source only. UI: org "Git credentials" page + per-app select + build_args/secrets editors on the Advanced tab (secrets masked, plaintext admin-only). Deferred: SSH deploy-keys.

**Multi-server (cluster):** Stage 1+2 merged to master, live-checked on 2 nodes. **Model: 1 control-plane Krill + N worker nodes** (NOT N installs). Engine swarm methods (`Nodes`/`NodeSetAvailability`/`NodeRemove`/`SwarmWorkerToken`/`ServiceTasks`/`NodeSetLabel`/`NodeDeleteLabel`); `cluster_nodes` table (migration 000022; SSH access, key `secret.Enc`) is a **global** (NOT org-scoped) infra resource gated by **`RequireInstanceAdmin`** (`users.is_admin`), NOT org-scoped RoleAdmin — see §4; `internal/cluster` SSH-joins workers (`docker swarm join`, accept-new host-key); the Nodes page (list + add-by-SSH / drain / remove) is instance-admin-only (non-operators get 404) + `KRILL_ADVERTISE_ADDR`; the control-plane node is guarded from drain/remove. Placement (migration 000023 `applications.placement_mode`/`placement_nodes`, `postgres_dbs`/`redis_dbs.node_hostname` at the time — carried forward as `db_instances.node_hostname` by migration 000029; migration 000024 node labels): `ServiceSpec.Global`/`SpreadNodeID` in `buildSwarmSpec`; any/pin/global modes reconciled via `krill.place.<appID>` labels; a DB instance pins to a chosen node (`node.hostname==X`, node-local volume, apps reach it over overlay DNS). Deferred: stateful HA/replication, HA control-plane, network storage, per-replica hard pin.

**GitHub auto-deploy (Phase 6):** per-app, opt-in (`applications.auto_deploy`, default false; migration 000026), **webhook + PAT** (no OAuth/GitHub App). One per-app secret (`webhook_secret`, `secret.Enc`) serves both mechanisms; kept across disable→enable. Two PUBLIC endpoints registered before the `RequireAuth` group (auth is the secret, not a cookie; `csrfGuard` exempts the `/webhooks/` prefix): **Dockerfile/git apps** → `POST /webhooks/github/{appID}` verifies HMAC `X-Hub-Signature-256` (`webhook.VerifyHMAC`, constant-time), matches `ref` to `git_branch`, then `deployer.Enqueue(appID,"webhook")` → build+deploy (`ping`/unknown event/non-matching branch → 200 no-op; **bad sig → 404**, same as unknown/disabled/wrong source_type → so the endpoint never leaks which app IDs have auto-deploy enabled). **Image apps** → `POST /webhooks/deploy/{appID}` checks the secret from the `Authorization: Bearer` header only — `?token=` is not read (constant-time, empty stored secret rejected explicitly; bad token → 404); when the deploy cannot be queued (a deploy of that app is already in flight, or the organization is at `KRILL_MAX_BUILDS_PER_ORG`) both webhook endpoints answer **503 with `Retry-After`** instead of a silent 202, and the deploy hook refuses before retagging and restores the previous tag on any refusal, optional `?tag=` (`webhook.ValidTag` → `UpdateApplicationImage`), then re-pull+deploy; the CI calls it after `docker push`. Both endpoints answer **503 + `Retry-After: 30`** when the deployer refuses the deploy (already in flight for the app, the per-org `KRILL_MAX_BUILDS_PER_ORG` cap, a full queue) instead of acknowledging a deploy that never happened; the deploy hook refuses before retagging when the app already has a deploy in flight, and puts the previous tag back when the enqueue itself is refused. The pure helper package is `internal/webhook` (`VerifyHMAC`/`ParsePushEvent`/`NewSecret`/`ConstantTimeEqual`/`ValidTag`, no GitHub SDK). Admin handlers `enableAutoDeploy`/`disableAutoDeploy`/`regenerateWebhookSecret` (admin-gated, tenant-chain) + a General-tab Auto-Deploy section (URL + masked secret reveal/copy + Regenerate, admin-only; webhook URL built from `Config.BaseURL()` ← `KRILL_PUBLIC_URL` or `KRILL_HOST`+scheme). **Same-tag re-pull fix:** `Engine.ResolveDigest` (registry `DistributionInspect`, no pull) pins image apps to `repo@sha256:…` in the deployer so a redeploy of an unchanged tag (`:latest`) actually pulls the new image (best-effort: `slog.Warn` + plain-tag fallback on error). Deferred: OAuth/GitHub App, repo/branch picker, auto-creating the webhook in GitHub, native GHCR `registry_package`, coalescing rapid pushes. See `docs/superpowers/specs/2026-06-20-krill-phase6-github-autodeploy-design.md`.

**DB instances (2026-07):** the one-container-per-database managed-DB model is gone, replaced by org-level `db_instances` (Postgres/Redis servers, one Swarm service per instance, optionally pinned to a node) + env-scoped `logical_databases` living inside a Postgres instance. Creating a logical DB provisions it synchronously via `Engine.Exec` piping SQL into `psql` on stdin inside the instance's container — `CREATE USER`/`CREATE DATABASE ... OWNER ...`/`REVOKE CONNECT ON DATABASE ... FROM PUBLIC` (`internal/dbservice/provision.go`; full drop-compensation on any mid-way failure so a retry is safe). Redis instances still serve apps directly — no logical sub-resource, one instance = one connection target. `app_db_links` now points at real FKs (`logical_database_id` XOR `instance_id`, CHECK-enforced) instead of a loose `engine`+`db_id` pair, and `backups` target `logical_database_id` with a per-database S3 layout (`<prefix>/<app_name>/<db_name>/<ts>.sql.gz`, one directory per logical database so retention never mixes dumps from different databases in the same instance). Migrations `000029` (create `db_instances`/`logical_databases`, convert every legacy `postgres_dbs`/`redis_dbs` row into an instance in place — collision-safe across engines, no container recreation, existing volumes/services keep running) and `000030` (drop the legacy `postgres_dbs`/`redis_dbs` tables + the transitional `legacy_*`/`engine`/`db_id`/`postgres_db_id` columns) are both in. Changing a DB instance's node now migrates its data volume (stop→stream→redeploy on the target node, fail-safe rollback to the source on any error; capped by `KRILL_MIGRATE_TIMEOUT`) (code-complete; live cluster acceptance pending — see ROADMAP acceptance queue). UI: an org-level Database Servers page (`/orgs/{id}/db-servers` — create/deploy/start/stop/version/node/delete) + reworked environment Databases tabs (create/detail/delete/backups, now under `/projects/{p}/environments/{e}/databases`). See `docs/superpowers/specs/2026-07-02-krill-db-instances-design.md` and `docs/superpowers/plans/2026-07-02-krill-db-instances.md`.

**Stateful services — engine drivers (MinIO + DragonFly, 2026-07-08):** managed engines are now **driver-based**. Per-engine knowledge (image/spec/args/env/mounts/health, external-access ports, app-link fields, connection display) lives in a leaf package `internal/dbservice/drivers` (imports docker+secret only, so both `dbservice` and `deploy` depend on it with no cycle): a `Driver` per engine registered in `drivers.Registry` (`postgres`/`redis`/`dragonfly`/`minio`), with `dbservice.Instance` a type-alias of `drivers.Instance`. The old switch/if engine special-cases collapsed into driver dispatch — `instanceSpec`→`Driver.BuildSpec`, `reconcileProxy`→`Driver.ExternalTargets`, detail conn block→`Driver.ConnDisplay`, deploy-time app-link resolver→`drivers.LinkValue(engine, src, field)`; `Driver.HasLogicalResource()` gates logical-DB provisioning (postgres-only — `provision.go` unchanged). postgres/redis were refactored into drivers behavior-for-behavior (regression tests assert the specs are unchanged). **DragonFly** (`dragonflyDriver` embeds `redisDriver`): Redis-compatible (RESP), image `docker.dragonflydb.io/dragonflydb/dragonfly`, args `["dragonfly","--requirepass",pw]`, port 6379, superuser `default`; conn/link fields identical to redis, so an existing redis app-link works unchanged. **MinIO** (`minioDriver`): S3-compatible, image `drivers.MinIOImage` = `quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z` (Docker Hub removed `minio/minio`, and MinIO no longer publishes community builds, so the tag is pinned rather than a frozen `latest`; `internal/testutil.NewMinio` runs the same constant), args `["server","/data","--console-address",":9001"]`, env `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` (root user is user-chosen at create, validated `^[a-zA-Z0-9]{3,63}$`; password generated), **two external ports** — S3 API 9000 + console 9001 — so `ExternalTargets` returns 2 targets and `reconcileProxy` (generalized from B2's one-socat-per-instance to N targets per `Suffix`) raises `krill-dbproxy-<id>` (S3) + `krill-dbproxy-<id>-console`; healthcheck omitted in v1. App-linking is **engine-aware**: `app_db_links.field` CHECK (migration 000037) adds S3 fields `endpoint`/`access_key`/`secret_key`/`region` alongside the pg/redis-shaped set; the add-form's `db_ref` uses kind `pg:<logical_db_id>` (postgres, via logical DB) or `inst:<instance_id>` (any non-postgres instance — redis/dragonfly/minio), the Field `<select>` filters options by the target engine (JS `data-engine`/`data-engines`, server-validated against `Driver.LinkFields()`), and `drivers.LinkValue` resolves minio to `endpoint=http://<app>:9000` / `access_key=<root user>` / `secret_key=<pw via secret.Dec>` / `region=us-east-1`. **Instance-only in v1** (no env-scoped buckets/indexes — the app creates its own); no backups for the non-pg engines (backups stay `logical_database_id`-scoped, i.e. postgres-only). Three additive migrations: `000035` (`db_instances.console_external_port` + partial unique index), `000036` (recreate the engine CHECK allowing `postgres|redis|dragonfly|minio`), `000037` (`app_db_links_field_chk` + S3 fields). Deferred: OpenSearch (host `vm.max_map_count`/JVM-heap too heavy for the 1.9 GB VPS — same driver later), env-scoped sub-resources (buckets/indices → a future `logical_resources`), a Traefik domain for the MinIO console, and MinIO/DragonFly backups (incl. managed-MinIO as a Krill S3 destination). See `docs/superpowers/specs/2026-07-08-krill-stateful-services-minio-dragonfly-design.md` / `docs/superpowers/plans/2026-07-08-krill-stateful-services-minio-dragonfly.md`. **Single-writer protection (2026-09-18):** every driver's `BuildSpec` now sets `docker.ServiceSpec.UpdateStopFirst: true` (a live cluster caught two Postgres postmasters on one `PGDATA` for ~0.5s during a worker-node return); postgres/redis/dragonfly additionally wrap their `Command` in a portable `sh -c 'exec 9<"$0" && flock 9 && exec <entrypoint> "$@"' <MountTarget()>` to lock the volume's own mount-point directory against a second container appearing outside a service update too (a node returning mid-reconciliation is not one) — NOT `flock --no-fork`, which busybox (every alpine-tagged image) doesn't support. MinIO's image has no `flock`, so it keeps stop-first only — see **Two processes on one managed-DB data directory** in §3 and [Nodes](docs/architecture.md#nodes).

**Topology (visual cluster map):** a read-only, org-scoped page (`RequireRole(RoleAdmin)`, NOT `RequireInstanceAdmin` — it only ever exposes the org's own apps/DB instances/links) at `/orgs/{id}/topology` (+ `/topology/data` JSON) draws node lanes (control-plane + workers from `engine.Nodes`) holding the org's apps and DB instances by actual placement, resolved via the new `docker.Engine.Tasks` method (one `ServiceList`+`NodeList`+`TaskList` sweep for every service's node, instead of a per-service `ServiceTasks` call). Logical databases render as chips inside their Postgres instance's box; `app_db_links` draw as colored threads (color = target engine Postgres/Redis; a cross-node thread — app and DB on different nodes — renders thicker + dashed). **v2** (2026-07-05) adds: an **Ingress lane** (Internet → the `krill-traefik` gateway service → exposed app, edge labelled with the domain from `ListDomainsByApplication`), directional arrows (SVG markers) on every edge, connection **detection from raw `env_text` DSNs** (`topology.DetectEnvLinks` scans each app's parsed env for `<db_instance_app_name>:5432`/`:6379`, matching down to the logical database when a `/<db_name>` suffix is present) alongside the modeled `app_db_links` (deduped — a modeled link wins over a detected one to the same target), and collapsing of multiple per-field links from one app to the same DB into a single thread. Pure `internal/topology` package (`Build`, `DetectEnvLinks`, graph types `Graph`/`GNode`/`GService`/`GDB`/`GLink`) — no DB/docker access itself, fed by a thin adapter in `internal/server/topology_handlers.go`. **No migration, no new SQL query** (v2 only adds an exported `traefik.ServiceName` const, replacing an inline literal). Client is an inline-SVG vanilla-JS island (`.k-topo` / `mountTopology` in `app.js`, fetch-once on mount + a manual "Refresh" button, no polling). See `docs/superpowers/specs/2026-07-04-krill-topology-graph-design.md` / `docs/superpowers/plans/2026-07-04-krill-topology-graph.md` (v1) and `docs/superpowers/specs/2026-07-05-krill-topology-v2-ingress-design.md` / `docs/superpowers/plans/2026-07-05-krill-topology-v2-ingress.md` (v2).

**Agent API — MCP + REST (2026-08-13):** twelve agent-facing operations over apps that **already exist**, living in one transport-agnostic service layer (`internal/api`, tenancy + level gate inside) with two thin adapters: **REST** `/api/v1/*` (`internal/server/api_handlers.go`) for CI/scripts and **MCP** streamable HTTP at `/mcp` (`internal/mcpsrv`, `github.com/modelcontextprotocol/go-sdk` v1.2.0). Read tools/routes: `krill_whoami`, `krill_list_apps`, `krill_app_status`, `krill_app_logs`, `krill_deployments`, `krill_deployment_status`, `krill_list_env` (`GET /api/v1/whoami|apps|apps/{app}|apps/{app}/logs|apps/{app}/deployments|deployments/{id}|apps/{app}/env`). Write: `krill_deploy`, `krill_rebuild`, `krill_reload`, `krill_stop`, `krill_set_env` (`POST /api/v1/apps/{app}/{deploy|rebuild|reload|stop|env}`). **There are no destructive operations at all** — nothing creates or deletes an org/project/environment/app/DB/domain/volume, and there is no `docker exec`/terminal; the blast radius is bounded by the surface, not by a permission matrix (a list of twelve is checkable by eye). `{app}` is a numeric id or a `project/environment/app` path (`api.Service.resolveApp`; cross-org ⇒ **404, never 403**). **Auth:** org-scoped bearer tokens in `api_tokens` (**migration 000040**) — `krill_pat_<32B base64url>`, stored as SHA-256 + an 8-char lookup prefix (index NOT unique; candidates are compared constant-time), plaintext shown **once** via the `krill_flash_token` one-shot cookie and unrecoverable. `Identity.CanWrite()` = token `level` ∩ the owner's **live** role (`>= RoleAdmin`), re-resolved by `Authenticator.Authenticate` on every request — demoting or removing the member kills their write token instantly, with no revocation step. `RequireAPIToken` (`internal/server/api_middleware.go`) accepts the token **only** from `Authorization: Bearer` (never `?token=` — query strings land in proxy logs/history), rate-limits **60 req/min per token** (429 + `Retry-After`), and stashes the Identity via `api.WithIdentity` — which is why the identity ctx key lives in `internal/api` (`internal/mcpsrv` must not import `internal/server`; that would cycle). Both surfaces are registered BEFORE the `RequireAuth` group and exempted from `csrfGuard` (an MCP client sends no `Origin`); the ONE `mcpsrv` handler instance is mounted at both `/mcp` and `/mcp/*` (it owns the `Mcp-Session-Id` session table — two instances would lose sessions). **`KRILL_AGENT_API_ENABLED` (default true) gates BOTH surfaces** — false leaves the authenticator unwired and `/api/v1` 404s too. (It was `KRILL_MCP_ENABLED` until 2026-08-13; renamed because it never gated MCP alone.) Deploys are **async** (`{deployment_id, status}` → poll `krill_deployment_status`); logs are bounded (runtime tail default 200 / max 1000, build-log tail ~8 KB); **`krill_list_env` returns names + source (`literal`/`db-link`) and NEVER values** (everything an agent reads reaches its model provider); `krill_set_env` edits a single `env_text` line (order/comments preserved, duplicate key ⇒ conflict) and does **not** redeploy. Errors are `api.Error{Code,Message}` → HTTP status (REST) / `isError` text (MCP); internal errors never leak `err.Error()` (generic text + `request_id`). Every write logs an INFO audit line with `token_id`/`user_id` (never the token, never an env value); at startup a non-`https` public URL with the API enabled logs a warn. UI: Settings → **API tokens** (`/orgs/{id}/api-tokens`; create is admin-gated, list/revoke only need membership and only ever touch the caller's own tokens). Agent-side runbooks live in [`skills/krill-deploy/SKILL.md`](./skills/krill-deploy/SKILL.md). Live acceptance (no MCP client has connected yet) is queued in ROADMAP. See `docs/superpowers/specs/2026-08-13-krill-mcp-agent-api-design.md` / `docs/superpowers/plans/2026-08-13-krill-mcp-agent-api.md`.

## 2. Build / run / test (exact commands)

THE most important gotcha — DB/integration tests REQUIRE the Colima testcontainers env. Always run tests via `make test`. It auto-sets both env vars that Ryuk (testcontainers cleanup) needs on Colima's virtiofs:

```
DOCKER_HOST=unix://$HOME/.colima/default/docker.sock        # host socket path
TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock  # in-VM socket path
```

Without BOTH set, tests false-fail with a socket-mount error. NEVER report "Docker not running" without first trying this env. If you cannot use `make`, run the same command manually:

```
DOCKER_HOST=unix://$HOME/.colima/default/docker.sock \
TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock \
go test ./...
```

After editing any `.templ` or `.sql` file you MUST run `make generate` — generated code (`*_templ.go`, `internal/database/gen/*.sql.go`, and `internal/web/static/app.css`) is committed to the repo and the build uses it.

**Web terminal (Phase 7):** admin-only interactive `docker exec` into a running app container via xterm + WebSocket. `docker.ExecInteractive` returns an `ExecSession` (TTY, raw stream); the admin-gated `appTerminal` WS handler runs `pumpTerminal` (binary frames = stdin, text frames = `{"rows","cols"}` resize, session output = binary back), with `KRILL_TERMINAL_IDLE_TIMEOUT` reaping idle sessions. Tenancy via `loadAppCtx`; session I/O is never logged; same-origin WS. Terminal tab on the app page (`/bin/sh` + command override). The live `docker exec` path is verified on a real host (no Swarm in unit tests). See `docs/superpowers/specs/2026-06-07-krill-phase7-web-terminal-design.md`.

**Monitoring (Phase 7 + cluster-wide):** **instance-admin-only** CPU/memory page (`/orgs/{id}/monitoring`, sidebar entry; the host-/cluster-wide view spans every tenant, so it is gated by `RequireInstanceAdmin` — NOT org-scoped RoleAdmin — and the sidebar/tab links show only for instance operators; non-operators get 404), now **cluster-wide**. A `metrics.Sampler` (`internal/metrics`) samples every `KRILL_METRICS_INTERVAL` into `metric_samples` (each row tagged with its `node`), pruned after `KRILL_METRICS_RETENTION`. The sampler drives a `metrics.ClusterSource` that collects the **control-plane node** (local daemon) plus **every `cluster_nodes` worker** in parallel: per worker it `cluster.DialVerified`s the stored SSH creds and forwards the remote `unix:///var/run/docker.sock` into a `docker.NewRemoteStats` client, reusing the same `statsCollector` (CPU% via `cpuPercent`, working-set memory; a per-connection `CPUCache` keyed by container ID — one per node so identical IDs don't mix). Each worker runs under `KRILL_METRICS_NODE_TIMEOUT`; an unreachable worker is warn-logged and skipped (the tick and other nodes proceed; the node renders **stale**). Per-node capacity (NCPU/MemTotal) is upserted into the `node_capacity` table each tick so `/monitoring/data` needs no SSH. `/monitoring/data?range=1h|6h|24h` returns a **per-node summary array** (`node`, cpu%, mem used/total, ncpu, containers, stale) + per-component series/rows tagged with `node` (series keyed by `(node, component)`), bucketed onto a shared grid (`metrics.GridTimes`/`BucketAvg`, nil = gap) and grouped by `metrics.Classify` (control/infra/app/db). The control-plane node is labelled `"control-plane"` (a friendly, stable name set in `cmd/krill/main.go`, matching the rest of the UI) rather than its raw Swarm hostname; workers use their `cluster_nodes.name` (e.g. `worker-1`). Each tick the sampler also `PruneCapacityExcept`s — dropping `node_capacity` for nodes no longer in the cluster (renamed/removed) so they stop showing as stale phantoms, while a still-listed-but-down worker stays (and renders stale). The client island `mountMonitoring` (`.k-mon`) draws uPlot CPU/mem charts + a per-node summary (one line per node) + a node-tagged grouped table (grouped by node header), and a **node selector** dropdown (All / per-node) that client-side-filters BOTH charts and table (series already carry `node`); the 10s poll timer is `window.__krillMonTimer`, cleared by `krillEnhance` on nav. The live `docker stats` path (local + SSH-tunnelled) is verified on a real host (no Swarm/SSH in unit tests). Migration `000027` adds `metric_samples.node` + `node_capacity`. See `docs/superpowers/specs/2026-06-08-krill-phase7-metrics-design.md` + `docs/superpowers/specs/2026-06-21-krill-cluster-monitoring-design.md`.

**Structured log viewer (Phase 7):** app + DB runtime logs render as a Dokploy-like table (time | level | message) instead of raw xterm. `ServiceLogs` requests docker `Timestamps`; `ParseLogLine` (`internal/logparse`, unit-tested — moved out of `internal/server` so `internal/api.AppLogs` can share it) strips the docker RFC3339 prefix and detects the level (logfmt `level=` or a leading INFO/WARN/ERROR/DEBUG/TRACE/FATAL/SUCCESS token); `streamParsedLogsToWS` sends `{t,lvl,msg}` JSON frames. The client island `mountLogViewer` (`.k-logs[data-ws]`) renders color-coded rows with text search + a level filter (Debug/Info/Warn/Error). Deploy/build logs (`DeployLogHub`, `.k-term[data-ws]`) and the interactive Terminal (`.k-term[data-term-ws]`) still use xterm. See `docs/superpowers/specs/2026-06-08-krill-phase7-log-viewer-design.md`.

**Notifications (Phase 7):** `internal/notify` sends Telegram alerts on failures + health transitions (deploy failed, backup failed, app down/recovered — no success spam). Org-scoped `notification_channels` (bot token encrypted via `secret`, masked in UI, never logged). Sources push events through tiny consumer-side interfaces (`deploy.Notifier` in `finish()`, `backup.Notifier` in `fail()`); a background `notify.Watcher` polls `ServiceStates` every `KRILL_HEALTH_POLL_INTERVAL` and alerts on healthy→down (debounce 2) / down→healthy transitions (in-memory state; an app never seen healthy stays silent — that case is covered by deploy-failure). Best-effort + async (detached ctx, 10s send timeout). Settings → Notifications (admin-only) + a "Send test message" button. See `docs/superpowers/specs/2026-06-07-krill-phase7-notifications-design.md`.

**Secrets & i18n:** secrets are encrypted via `internal/secret` (`secret.Enc` on write, `secret.Dec` on read) at the store boundaries (dbservice store, db/registry/destination handlers, deploy store, backup store). UI masks them: DB connection strings render `type=password` + eye-reveal (`krillReveal`); env values are masked by default with a Show/Hide toggle (`krillEnvRevealToggle`). The UI is bilingual: `internal/web/i18n` has `en` + `ru` catalogs (keep both in sync — same keys); locale comes from the `krill_lang` cookie (set by `POST /lang` via the Settings language selector); `i18n.T`/`i18n.Tf` (printf) look it up.

**Domains/TLS (Phase 5):** the `domains` table (host UNIQUE, tls, is_primary) is the routing source of truth; `applications.domain` is the denormalized primary. `traefik.AppLabels(serviceName, []traefik.Domain, port, network)` emits per-domain routers — non-TLS on `web`, TLS on `websecure` with `tls.certresolver=le` plus a `web`→HTTPS redirect router (no global redirect). Domain CRUD re-applies labels via `engine.ServiceUpdateLabels` (service-level labels only → no container restart). Traefik bootstrap adds `:443` + the `le` HTTP-01 resolver + the persistent `krill-traefik-acme` volume at `/letsencrypt`. Real ACME issuance is verified manually (needs public DNS); locally TLS stays off and sslip.io domains serve plain HTTP.

**Logging:** structured `slog`, configured in `cmd/krill/main.go` (`setupLogging`). One access-log line per request comes from the `requestLogger` middleware (`internal/server/logging.go`); 5xx logs at error level. In handlers use `logFrom(r)` — a `*slog.Logger` pre-tagged with `request_id`/`user_id`/`org_id` — for error logs (before any 5xx response) and INFO audit logs (before the success redirect). ## 3. Critical facts that bite

- **Traefik is pinned to `v3.6.1`** (`internal/traefik/bootstrap.go`, const `TraefikVersion`). Versions ≤3.6.0 hardcode Docker API 1.24, which Docker Engine 29.x rejects ("client version 1.24 is too old"), breaking the Swarm provider and all routing. v3.6.1 auto-negotiates the API version. Traefik is configured via CLI args only (no `traefik.yml`); the only mount is the docker socket (read-only).
- **Tailwind v4 is CSS-first.** There is NO `tailwind.config.js` and NO `@tailwind` directives. Config lives in `internal/web/styles/input.css` via `@import "tailwindcss"`, `@source "../templates"`, `@theme { ... }`, and `@layer components`. Regenerate with `make css` or `make generate`. The output `internal/web/static/app.css` is a committed artifact (generated, not hand-edited).
- **templ component-on-its-own-line gotcha.** A `@Component(...)` call inline after text renders as literal `@Component` text. Put component calls on their own node:
  ```
  <div>
    @StatusBadge(status)
  </div>
  ```
- **Native `<dialog>` modals need `margin: auto`.** Tailwind preflight resets `margin: 0` on `<dialog>`, pinning modals to the top-left. The `.k-modal` class in `input.css` restores `margin: auto` to center them.
- **Confirm dialogs + log terminals: `app.js` loads ONCE in the layout `<head>` (deferred), NOT per-tab.** Destructive forms carry `hx-boost="false"` + `data-confirm` (server-rendered i18n message) and call `krillConfirm` (styled `#k-confirm` modal) — native `confirm()` is broken under hx-boost. Log viewers are `<div class="k-term" data-ws=...>` (xterm.js/addon-fit.js loaded per log-tab, lazy); `krillEnhance` (on `DOMContentLoaded`+`htmx:afterSettle`) auto-mounts any `.k-term[data-ws]:not([data-mounted])` and inits the env editor — so do NOT add inline `mountLogTerminal`/`krillEnvMode` calls or per-tab `app.js`. `.k-term` needs an explicit height (CSS) or FitAddon computes 0 rows on a boosted swap.
- **DB log feeds use negative feed IDs to avoid colliding with positive deployment IDs.** The `DeployLogHub` lives in `internal/deploy/logs.go`; the feed-ID helper lives in `internal/dbservice/instance.go`: `InstanceFeedID(id) = -id` — one instance table now (unlike the legacy pg/redis pair, which needed two disjoint formulas), used by the `dbInstanceDeployLogs` WS handler.
- **A host-mode published port deadlocks a StartFirst update (2026-09-13).** The replacement task binds the same port on the same node, so Swarm leaves it `Pending` ("no suitable node (host-mode port conflict)") and — StartFirst — never stops the old task: the update neither finishes nor fails, the old spec keeps running, and nothing is logged. It hit Traefik (`:80`/`:443` in host mode, pinned to the manager): every gateway spec change after the first create (a new organization, the startup reconcile after an upgrade) silently left Traefik on its old networks. `buildSwarmSpec` now uses StopFirst for any service with a host-mode port (Traefik, raw TCP/UDP app ports, DB proxies — a brief gap instead of a hang), and `traefik.Reconcile` waits for the new task to run and for Swarm to mark the update `completed` (baseline-relative, 3 min — `completed` lands after the 5s update monitor, inside which Swarm can still roll back) and returns an error otherwise, so `gatewayReady` — and with it the org-network migration — means the gateway really joined the networks. Reconcile also refuses to trust a matching spec-hash label while the service's `UpdateState` is still `updating`/`paused`: the label is written with the spec, so an install stuck before the fix carries the current hash and would otherwise never be redeployed.
- **Changing `UpdateConfig.Order` itself takes effect in the very rollout that changes it, not the next one** — verified empirically (`internal/docker.TestUpdateOrderChangeAppliesInSameRollout`, `-tags=integration`): a service redeployed from a start-first spec to a stop-first spec in one `ServiceDeploy` call stops the old task before starting the new one for THAT deploy, not just for deploys after it. Nothing in the docker/swarm client API documents this either way, so it isn't safe to assume — this is what makes "an existing DB instance protects itself at its next deploy" (see **Stateful services** in §1) true without an extra scale-to-zero step.
- **Two processes on one managed-DB data directory (2026-09-18).** A live cluster caught two Postgres postmasters on the same `PGDATA` for ~0.5s during a worker-node return — the replacement task started before the old one (on the returning node) was confirmed gone. Fixed two ways, together: (1) `UpdateStopFirst: true` on every DB driver's spec (`internal/dbservice/drivers`) closes it for a service-spec update. A DB instance has no Reload/Rebuild (that's an app-only concept, see **App lifecycle controls**); its own actions are Deploy, Start, Stop, a version (image) change, a node move, and delete — Deploy/version-change/node-move all redeploy the service through the shared `deployCore` and so pick up the new spec, and so does `ParkInstance` (the org-network migration's way of moving a *stopped* instance onto its network without starting it — `StartInstance` only scales, so a parked instance would otherwise come back up on the old network), but **Start/Stop are `ServiceScale` only and reuse whatever spec is already running** — see the bullet above for why the very deploy that turns this on already rolls out stop-first; (2) each driver's `Command` wraps the container's own entrypoint in a *portable* flock, locking the volume's own mount-point directory (from `Driver.MountTarget()` — for Postgres the volume IS `PGDATA`, so the lock has to be the bare directory, not a file inside it, since `initdb` needs it empty on first start) — this is what closes a worker-node return, which is not a service update at all and `UpdateConfig.Order` cannot see. It is deliberately NOT `flock --no-fork`: busybox's `flock` — shipped by every alpine-tagged image, and the image is free text at create/version-change time (`postgres:16-alpine`, `redis:7-alpine`, ...) — has no `--no-fork` flag at all and fails outright ("flock: unrecognized option: no-fork"), which would crash-loop an alpine-based instance. Instead `Command` runs `sh -c 'exec 9<"$0" && flock 9 && exec <entrypoint> "$@"' <MountTarget()>`: opening the directory on a fixed fd and locking THAT FD (not a path) is understood by both util-linux's and busybox's `flock`, and per `flock(1)` the lock is not released when `flock` returns because the fd was already open on the command line — so it's held by the shell process itself through every later `exec` in the same process (the image's own privilege drop, then the real entrypoint) without needing to keep `flock` itself as PID 1. Postgres/Redis/DragonFly images ship both `sh` and `flock`; **MinIO's image has no `flock`**, so MinIO gets stop-first only, not the directory lock — recorded as an accepted gap, not fixed. A custom image missing either tool fails to start (missing `sh` surfaces as Docker's own "executable file not found"; missing `flock` surfaces as a shell error from inside the container, e.g. "flock: not found") — same tradeoff, recorded rather than special-cased. An existing instance is protected only once it goes through a Deploy, version change, or node move (whichever redeploys it with the new `Command`) — **a Start/Stop cycle does not**, so an instance that has only ever been started/stopped since this shipped is still exposed to a bad node return; Krill does not mass-redeploy every DB instance on upgrade, so redeploy instances holding real data right after upgrading Krill.
- **Literal `@` between two templ `{ }` expressions breaks the parser.** `@` starts a component-call token anywhere in templ text, not just right after other text — `{ a } @ { b }` fails to parse even though neither `a` nor `b` is a component. Build the whole string as one Go expression instead: `{ a + " @ " + b }` (see `database_detail.templ`'s `dbName @ instanceName` line).
- **`make generate`/sqlc does not prune orphaned generated files.** Deleting a `.sql` query file under `internal/database/queries/` and rerunning `make generate` leaves its previously generated `internal/database/gen/<name>.sql.go` in place untouched — sqlc only (re)generates from `.sql` files that still exist, it never diffs-and-deletes. The stale file still compiles (it's just Go + SQL strings, nothing checks the SQL against a live schema at build time), so the drift check stays green and dead code referencing dropped tables silently lingers. `git rm` the orphaned gen file by hand whenever a query file is deleted (e.g. `internal/database/gen/postgres_dbs.sql.go` when `internal/database/queries/postgres_dbs.sql` was dropped in migration 000030's cleanup).
- **Exec operations (logical-DB provisioning, pg_dump backups, restore, web terminal) are node-aware.** `Engine.Exec` and `ExecInteractive` locate the running task's node (`runningContainerID` → NodeID) and via an injectable `RemoteClientProvider` (wired in `cmd/krill/main.go`) select the docker client: local for control-plane, or remote via SSH tunnel to a worker's docker socket (`docker.NewRemoteClient` + `cluster.DialVerified`, lookup `cluster_nodes` by `swarm_node_id`). `cluster_nodes` holds only workers → a non-worker task = control-plane = local. Provider nil (tests / single-node) → always local. `ServiceLogs` already worked cross-node (Swarm API, not exec). **Docker-client opt-order gotcha (bit us on the live 3-node cluster):** in `NewRemoteClient`/`NewRemoteStats`, `client.WithHost("unix://…")` MUST come BEFORE `client.WithDialContext(dial)`. `WithHost` for a unix host calls `sockets.ConfigureTransport`, which OVERWRITES `transport.DialContext` with a local-socket dialer — so if `WithDialContext` runs first, the tunnel dialer is silently clobbered and the "remote" client talks to the LOCAL daemon (symptom: worker exec fails "No such container", and cluster monitoring silently reported the manager's stats as the worker's). Set the tunnel dialer LAST.
- **`secret.Dec` fails loudly (2026-08-05).** It returns `(string, error)`; a value carrying the `enc:v1:` tag that cannot be opened (missing, rotated or wrong `KRILL_SECRET_KEY`) yields `("", secret.ErrUndecryptable)` — never the stored ciphertext. Credentials feeding a real operation (deploy, backup, DB instance, bot token, node SSH key) fail the operation; display paths log and render nothing. Consequence on a live install whose key was rotated: those paths now break *visibly* instead of shipping a bogus password. Never reintroduce a `, _ :=` at a `secret.Dec` call.
- **A volume restore REPLACES the volume's contents (2026-08-05).** `VolumeRestore` clears the mount point (dotfiles included) before extracting, because `tar -x` alone only overwrites paths present in the archive — anything created after the backup used to survive, silently merging two points in time. Callers already quiesce the app first. Verified on real Docker by `TestVolumeRestoreReplacesExistingContent` (`-tags=integration`).
- **Named volume `<appName>-data` persists** for managed databases unless the user opts in via the "Destroy data" checkbox (`destroy_data=on`) on delete; only then is `engine.VolumeRemove()` called. Removal retries (`dbservice.removeVolume`) because right after `ServiceRemove` the volume is briefly "in use" while Swarm tears down the task container. **Deleting an environment or project destroys its managed-DB volumes** (`removeEnvDatabases` in `internal/server/project_handlers.go`, `destroy=true`) — otherwise the DB rows cascade-delete and the services/volumes would orphan with no UI to clean them.
- **golang-migrate's `Up()` fails on a schema newer than the embedded migrations** (`versionExists` → "no migration found for version N"). `database.RunMigrations` checks `m.Version()` first and, when the recorded version is ahead of `maxEmbeddedVersion()`, logs a warning and returns without calling `Up()` — this is what makes automatic rollback after a self-update possible (see **Self-update** in §1).
- **A failed or interrupted migration defeats the self-update rollback.** golang-migrate marks the schema dirty *before* running each migration and clean after it; a migration that fails, or a process killed mid-migration, leaves it dirty, and `RunMigrations` rejects a dirty schema before its newer-schema tolerance ever applies — so the reverted binary refuses to start too (`database schema is dirty at version N`). Recovery is manual (back up, fix the data/schema, `UPDATE schema_migrations SET dirty = false` once it matches N, or set `version = N-1` to re-run it — see `docs/install.md` Rollback). To keep a *signal* from causing it, `cmd/krill/main.go` runs migrations through `database.RunMigrationsContext` under its own `signal.NotifyContext(SIGINT, SIGTERM)` (the main signal handler is only registered at the end of `run()`): cancelling the context sends `true` on `m.GracefulStop`, which lets the in-flight migration finish and stops before the next one, and the call then returns `migrations stopped by shutdown: context canceled` even if nothing was left to apply. Only SIGKILL (including systemd's after `TimeoutStopSec`) or a crash can still leave the schema dirty.
- **Never restart `krill.service` from inside its own cgroup.** A child of the process (e.g. a `firewall.LocalRunner` command) running `systemctl restart krill` would itself be a member of `krill.service`'s cgroup, and the stop half of the restart (`KillMode=control-group`) SIGTERMs it along with the parent — reporting "signal: terminated" for a restart that is actually in progress. `selfupdate.Updater.restartCmd` instead schedules a transient `systemd-run` unit two seconds out to run the `systemctl restart`, from outside the cgroup entirely.
- **systemd's default start-rate limit (5 starts in 10s) parks a fast-failing unit in `failed`**, and `Restart=always` stops applying — hit by a crash-looping post-update binary, or by Postgres still starting after a reboot. Both `install.sh`'s unit and the self-update drop-in (`10-krill-update.conf`) set `StartLimitIntervalSec=0` so the unit just keeps retrying instead.
- **The pending self-update marker is written before the binary is renamed into place, not after.** Should the process die right between the two, the *new* binary starts, finds `krill-update-pending` and confirms itself instead of being reverted. Symmetrically, the revert script's first line is `[ -e $pending ] || exit 0` — `ConfirmStartup` deletes the marker before it cancels the revert timer, so a timer that still fires (a cancel that arrived too late) finds nothing to revert.
- **A `git describe` version (`v0.1.3-6-g1a09ec0`, `v0.1.3-dirty`) is valid semver but a prerelease**, so plain `semver.Compare` would rank it *older* than the release it descends from and "update" it backwards. `selfupdate.Newer`/`buildinfo.IsRelease` require the running binary's version to be a plain `vX.Y.Z` tag before it is ever offered an update — a `make build` or `go build` from a checkout never is.

## 4. Conventions (follow these)

- **Commit messages:** conventional-commits style (`feat(scope): ...`, `fix(scope): ...`, `test(...)`, `docs(...)`). HARD RULE: NO `Co-Authored-By` / Claude attribution trailers of any kind.
- **All UI strings go through `i18n.T(ctx, "key")`** with keys in the English catalog (`internal/web/i18n/en.go`). No raw user-facing literals in templates or handlers. The locale middleware (`WithLocale`) is currently a no-op (`en`); a second locale = a second map, no template changes.
- **Write everything in code in ENGLISH** — comments, `slog`/log messages, `fmt.Errorf`/`errors.New` strings, and `http.Error` messages. The codebase is English-only. The only Russian in the repository is the `ru` UI catalog (`internal/web/i18n/ru.go`); the maintainer's local, git-ignored notes under `docs/superpowers/` may be in Russian. Do not introduce Russian in `.go`, `.templ`, `.sql`, `.sh`, `.css`, or config files.
- **Every app/db route must chain-check tenant ownership and 404 on mismatch.** Load org → project → environment (and db) and verify each FK matches its parent (`loadOrg` → `loadProject` → `loadEnvironment` → `loadApp`/`loadDBChain`). Mismatch returns `http.NotFound`. There are IDOR regression tests; keep them green.
- **Handlers must NOT swallow errors** — log via `slog.Error("context", "err", err)` or return 500. No silent ignores in delete/deploy/version handlers.
- **Only an owner may grant the owner role** (`updateMemberRole` in `internal/server/org_handlers.go`) — prevents admin self-escalation.
- **Deploy waits for convergence before marking done — baseline-relative.** Before `ServiceDeploy` the deployer snapshots the service's task IDs (`engine.ServiceProgress(name, nil)`), then polls `ServiceProgress(name, baseline)` until `Running >= Desired` counting ONLY tasks outside the baseline (`KRILL_CONVERGE_TIMEOUT`, 1s interval). Counting all tasks (old `ServiceState` behavior) would declare every redeploy converged instantly on the old StartFirst task. A `rollback_*` `UpdateState` fails the deploy ("update rolled back").
- **Build logs are bounded** — head (128 KB) + tail (128 KB) buffer with a `...[truncated N bytes]...` marker only when the middle is actually dropped (`internal/deploy/logs.go`).
- **RBAC is owner > admin > member** (`Role` int with `RoleMember`/`RoleAdmin`/`RoleOwner` and `AtLeast`), enforced by `RequireRole(min)` middleware (403 if role < min). Admin+ can manage projects/apps/dbs/members; members are read-only.
- **Instance-operator vs org-admin (security-critical):** org-scoped `RoleAdmin` is **self-grantable** — any authenticated user can `POST /orgs` and becomes the new org's `owner`. So **global infrastructure (cluster nodes, the host-wide monitoring view) is gated by `RequireInstanceAdmin`**, backed by the instance-level flag `users.is_admin` (migration 000028), NOT by org-scoped RoleAdmin. Only the seeded `KRILL_ADMIN_EMAIL` user is promoted to `is_admin=true` on startup (`SeedAdmin`, idempotent); everyone else defaults false. `WithInstanceAdmin` loads the flag once per authed request into the ctx; `RequireInstanceAdmin` 404s non-operators (no capability disclosure). Do NOT gate a global/cross-tenant resource on `RequireRole` — use `RequireInstanceAdmin`.
- **Login hardening:** the unknown-email path runs a dummy bcrypt (`auth.dummyHash`) so it costs the same as a real check (no user-enumeration timing oracle); `POST /login` is per-source-IP rate-limited (`internal/server/ratelimit.go`, 10/min).
- **App mutations and DB secrets are admin-gated** (2026-06-06 hardening): the app POST routes (deploy/rebuild/reload/stop/env/advanced) and the DB backup download/objects routes sit inside a `RequireRole(RoleAdmin)` group in `server.go`; plaintext connection-string display is admin-only too. Members are read-only viewers — no deploys, no DB dumps/creds.
- **`external_port` is validated and conflict-checked** — `strconv.Atoi` + range `1..65535` → 400 on bad input; pre-check existing ports → 400 on duplicate.
- **Temp passwords flow via HttpOnly flash cookie** (`krill_flash_pw`), never in the URL; the template reads it once then clears it.
- **Unique-violation detection uses `errors.As(*pgconn.PgError)` + code `23505`** (`mapUniqueErr` in `internal/org/service.go`), not string matching.
- **Migrations must keep the previous release bootable (expand/contract).** A migration may only be additive relative to the release before it: new tables, new columns that are nullable or carry a `DEFAULT`, new non-unique indexes. New unique indexes and foreign keys on existing tables are not additive, an index the previous release relies on for `ON CONFLICT` must never be dropped, and the previous binary must tolerate any new enum/CHECK value the new one writes — widen reads a release before widening writes. `DROP COLUMN`/`DROP TABLE`/`RENAME`/`ALTER COLUMN ... TYPE`/`ALTER COLUMN ... SET NOT NULL`/`DROP NOT NULL`/`ADD COLUMN ... NOT NULL` without a default are only safe one release after the code has stopped using the old shape. Dropping a constraint is always fine; adding a `CHECK` is only safe when it cannot reject anything the previous release writes (the repo's drop-and-recreate-wider pattern, e.g. 000033/000036/000037/000038). The reason for all of this: self-update (see **Self-update** in §1) rolls back to the previous binary on a failed upgrade, and that binary must still start against the schema the newer one left behind — `database.RunMigrations` (`internal/database/migrate.go`) already tolerates this by skipping `Up()` (with a `slog.Warn`) when the recorded schema version is ahead of what the binary embeds, instead of failing with "no migration found". **Enforcement:** [squawk](https://squawkhq.com) (a Postgres migration linter with a real SQL parser, pinned and checksum-verified by `./tools/get-squawk.sh` into the git-ignored `tools/squawk`) runs as `make lint-migrations` in CI on every `*.up.sql` numbered above `MIGRATION_COMPAT_FROM` (46). `.squawk.toml` keeps only the backward-compatibility rules (`ban-drop-column`, `ban-drop-table`, `renaming-column`, `renaming-table`, `changing-column-type`, `adding-not-nullable-field`, `adding-required-field`, `disallowed-unique-constraint`, `adding-foreign-key-constraint`, `ban-drop-not-null`) and excludes every other rule by name; `assume_in_transaction = true` matches how the file really runs and keeps a UNIQUE/FK added to a table created earlier in the same file from being flagged. The target also self-checks against `internal/database/testdata/squawk/`: `breaking.sql` must report every `-- expect: <rule>` it lists, `compatible.sql` must pass — upgrading squawk means re-checking both and classifying any new rule in `.squawk.toml`. squawk checks the mechanical cases only; reviewers still read every migration, because it does NOT catch a new or tightened `CHECK`, enum widening, dropping an index used by `ON CONFLICT`, or `CREATE UNIQUE INDEX` on an existing table (`disallowed-unique-constraint` only fires on `ADD CONSTRAINT ... UNIQUE`). The escape hatch for an intentional break is `-- squawk-ignore <rule>` on the line directly before the line squawk reports, with the reason and the release from which it is safe after a second `--` on the same line (`-- squawk-ignore ban-drop-column -- safe from v0.5.0: nothing since v0.4.0 reads it`) or on a comment line above it — a comment line *between* the ignore and the statement makes squawk report the statement anyway, and in a multi-line statement squawk reports the offending clause's line (e.g. `DROP COLUMN`), not the statement's first line.

## 5. Architecture map

Runtime topology: a single Go binary (HTTP on `:8080`/`:18080`) holds all state in PostgreSQL (pgxpool) and drives a single-node Docker Swarm via the Docker API. Traefik (a Swarm service on host `:80`) watches the Swarm API and routes by `Host` header to app/db services, each on its own organization's overlay network (`krill-org-<id>`; Traefik is attached to all of them) — see **Per-organization networks** in §1. One deployment worker goroutine serializes all build/deploy jobs.

Packages:

- **`cmd/krill`** — entry point: load config → migrate → pgxpool + sqlc → seed admin/default org → wire services → bootstrap Traefik+network → start chi server → graceful shutdown.
- **`internal/config`** — env parsing via caarlos0/env (`Config`, `Load()`).
- **`internal/server`** — chi router, middleware chain, all handlers; path-scoped multi-tenant routes. Tenancy chain-checks `loadOrg`/`loadProject`/`loadEnvironment`/`loadApp` live in `context.go`; `loadDBChain` lives in `db_handlers.go`.

- **`internal/buildinfo`** — `Version` (linker-stamped by `release.yml`/`make build` via `-X ...buildinfo.Version=<tag>`, else derived from Go module/VCS build info, else `"dev"`), `String()`, `IsRelease(v)` (a plain `vX.Y.Z` tag, no prerelease suffix).

- **`internal/web`** — embedded static (`Static()` in `embed.go`), i18n (`WithLocale`, `T`, `en` catalog), templ templates (`layout`, `login`, `orgs`, `org_dashboard`, `project`, `app_detail`, `database_detail`, `deployments`, `members`, `status_badge`, plus shared `ui/components`).

- **`internal/topology`** — pure cluster-topology graph builder (`Build`, `DetectEnvLinks`) for the Topology page: nodes/services/DB-link assembly + `env_text`-DSN link detection, no DB/docker access of its own.
- **`internal/api`** — the agent-facing service layer: token generation/hashing (`GenerateToken`/`HashToken`/`TokenMatches`/`PrefixOf`), `Authenticator` (prefix lookup → constant-time hash compare → live membership), `Identity`/`CanWrite`, the identity ctx key (`WithIdentity`/`IdentityFrom`), `Error{Code,Message}`, and the twelve operations (`Whoami`/`ListApps`/`AppStatus`/`AppLogs`/`ListEnv`/`ListDeployments`/`DeploymentStatus`/`Deploy`/`Rebuild`/`Reload`/`Stop`/`SetEnv`). Key facts:
- For a `db_instances` row, `app_name` is UNIQUE and is simultaneously the Swarm **service name = internal DNS hostname = volume name prefix** (`<appName>-data`); it's generated once (`dbservice.GenerateAppName`, `krill-<engine>-<slug>-<rand6>`) and never changes, even across a name edit. A `logical_databases` row has no service of its own — it's a database + owner user inside its instance's container (`db_name`/`username`, `UNIQUE(instance_id, db_name)` and `UNIQUE(environment_id, name)`).
- `db_instances.external_port` is a nullable `*int32` (sqlc `emit_pointers_for_null_types: true`); conflicts checked via `CountDBInstancesByExternalPort` / `CountAppPortsByHostPort` (raw TCP/UDP app ports share the same host-port space) and enforced by a partial UNIQUE index (`WHERE external_port IS NOT NULL`, migration 000010 originally, recreated on `db_instances` by migration 000029).
- DB **credentials/passwords are stored plaintext** (no encryption at rest).
- `applications.env_text` (TEXT) is the SINGLE source for env vars — raw, ORDER-PRESERVING `KEY=VALUE` lines (the editor shows `c.App.EnvText`; no re-sorting). The deploy map is derived at runtime (`deploy.parseEnvText`); the old JSONB `env` map column was dropped (migration 000014). `parseEnv` (server) returns the map **and** duplicate keys → `saveEnv` rejects dupes. `applications.domain` has a UNIQUE index; `source_type` CHECK (`image`/`dockerfile`). Advanced container columns (migration 000008): nullable `memory_limit`/`cpu_limit` (TEXT, human units), `replicas` (default 1), `restart_condition` CHECK (`any`/`on-failure`/`none`), `restart_max_attempts`, and `healthcheck_*` (cmd/interval/timeout/retries/start_period). Nullable `command` (migration 000012, TEXT) is an optional container CMD override — `docker.SplitCommand` whitespace-splits it into `ServiceSpec.Args` (overrides the image CMD, keeps ENTRYPOINT; e.g. `start-dev` for Keycloak). Edited on the Advanced tab via `saveAdvanced`.
- `domains` (migration 000009) has `exposed` (BOOLEAN, default false — new domains are internal-only) and `paths` (TEXT, comma-separated path prefixes; empty = whole host) driving Traefik route exposure.
- `deployments` is append-only history: `status` CHECK (`running`/`done`/`error`), `trigger` CHECK (`manual`/`webhook`/`schedule`), index `(application_id, started_at DESC)`; `ClearOldDeploymentLogs` empties the `log` field for rows finished >1h ago (keeps metadata); `ListDeploymentsByApplication` returns last 50.
- All `timestamptz` map to Go `time.Time`. sqlc config (`sqlc.yaml`): schema `internal/database/migrations`, queries `internal/database/queries`, package `db`, out `internal/database/gen`, `pgx/v5`, `emit_interface`/`emit_json_tags` on.

Brainstorm → spec (`docs/superpowers/specs/`, date-prefixed) → plan (`docs/superpowers/plans/`, date-prefixed) → subagent-driven execution.

**Public docs layout (2026-09-13):** `README.md` is a short landing page (badges, screenshots from `docs/images/`, features, quick start, status, a docs index) — keep it short and put detail in `docs/`. User and operator documentation lives in `docs/install.md` (install, upgrade, external Postgres, uninstall), `docs/configuration.md` (every `KRILL_*` variable — add a new one here, it is the only full list), `docs/guides/` (domains, backups, registries, agent-api, krill-cli) and `docs/architecture.md`; contributor docs in `docs/development.md` and `CONTRIBUTING.md`. Only `docs/superpowers/` is git-ignored.

- Subagents run STRICTLY SEQUENTIALLY (parallel execution reordered/duplicated tool calls — see Gotchas).
- Subagents do NOT commit on master; the harness blocks it. Only the controller commits.
- Always verify with `make test` before committing.

## 8. Gotchas / lessons (don't repeat these)

- **Parallel subagents reorder/duplicate tool calls** — run subagents sequentially.
- **Traefik API mismatch → routing breaks** when not pinned to ≥v3.6.1 against Docker Engine 29.x (see §3).
- **`StatusBadge` (and any templ component) rendered as literal text** when placed inline after text on the same line — give it its own node.
- **Modals pinned top-left** because Tailwind preflight zeroes `<dialog>` margins — use `.k-modal` (`margin: auto`).
- **CHECK-constraint violations in tests** when omitting `SourceType` (must be `image` or `dockerfile`) or supplying an out-of-set `status`/`trigger`/`role`. Always set CHECK-constrained columns to valid values in fixtures.
- **Tests false-fail with a socket-mount error** off the Colima env — always use `make test` (see §2).
- **Literal `@` as text between two templ expressions doesn't parse** — `{ a } @ { b }` fails; concatenate into one expression instead (see §3).
- **`make generate`/sqlc leaves orphaned `.sql.go` files behind** when their source `.sql` query file is deleted — `git rm` them by hand (see §3).

## 10. Docker & CI

- **`Dockerfile`** — multi-stage: `golang:1.26.1-alpine` builder → `CGO_ENABLED=0` static binary → `gcr.io/distroless/static-debian12:nonroot` (~25 MB, runs as UID 65532). It relies on the COMMITTED generated files (no `make generate` in-image); migrations (`//go:embed migrations/*.sql`) and static assets (`//go:embed all:static`) are embedded, so the final image is binary-only. Build locally: `docker build -t krill:local .`.
- **`.github/workflows/ci.yml`** — push (all branches) + PR: build/vet/test (testcontainers works on the runner's native Docker — do NOT add the Colima socket override here), a no-push Docker build, and a generated-drift check (`make generate` + `git diff --exit-code`).
- **`.github/workflows/release.yml`** — `v*.*.*` tag (or `workflow_dispatch`): multi-arch buildx → push to `ghcr.io/${{ github.repository_owner }}/krill` → GitHub Release on tag pushes. On a tag it ALSO cross-compiles static binaries (`krill-linux-amd64`/`krill-linux-arm64`, `CGO_ENABLED=0`, committed generated files) + a `checksums.txt` and attaches them as Release assets — these are what `install.sh` downloads. Both the binaries and the image are stamped with the same version: `-X github.com/proshik/krill/internal/buildinfo.Version=<tag>` on the Go builds, `VERSION=<tag>` as the Docker build-arg — `krill --version` reports the release tag either way. Uses `GITHUB_TOKEN`; needs `permissions: packages: write` + `contents: write`. A package published from this public repository comes out public: `ghcr.io/proshik/krill` pulled anonymously right after v0.1.0, with image tags `0.1.0`, `0.1`, `latest` and `sha-<commit>` (no leading `v`).
- **`install.sh`** (repo root) — VPS one-liner (`curl -sSL …/master/install.sh | sudo sh`): host binary + systemd (NOT a container), idempotent (re-run = upgrade). Installs Docker if missing → `swarm init` → loopback-only `krill-postgres` container for state, on its own `krill-state` Docker network rather than the default bridge (a build container also sits on the default bridge and could otherwise reach Postgres by IP even with the loopback-only port publish; an upgrade from an older install removes and recreates the container to move it — same volume, same data) → downloads the checksum-verified release binary (fail-closed: missing `checksums.txt`/entry aborts unless `KRILL_SKIP_VERIFY=1`) → generates `/etc/krill/krill.env` (admin pw + `KRILL_SECRET_KEY` created once, preserved on re-run; `KRILL_COOKIE_SECURE=false` — it stays false; the UI gets HTTPS from **Settings → Panel domain**, not from this flag) → `krill.service` (`StartLimitIntervalSec=0`, so a fast-failing unit — Postgres not up yet after a reboot, a broken upgrade — keeps retrying instead of landing in `failed`; the self-update drop-in sets the same thing for a unit installed before this). Variant A (host binary) was chosen over a Swarm-service install to avoid the nonroot-socket and self-exposure chicken-and-egg. See `docs/superpowers/specs/2026-06-09-krill-installer-design.md`.
- After changing the build/embed setup, re-verify by actually building the image (`docker build .`) and confirming it still runs (`docker run --rm krill:local` should fail fast on the missing `KRILL_DATABASE_URL`).
