# Operations: self-update, state backup, observability, notifications, logs

Everything that keeps a running install observable and upgradable, plus the release image and installer.

## Self-update

an instance admin installs a newer Krill release from **Settings → Updates** without touching the host. `internal/buildinfo.Version` (linker-stamped by `release.yml` and by `make build`'s `git describe`) is what `buildinfo.IsRelease`/`selfupdate.Newer` compare against a `selfupdate.Checker`, which discovers the latest tag via GitHub's unauthenticated `releases/latest` redirect (no API, no rate limit) on a timer (`KRILL_UPDATE_CHECK_INTERVAL`) and on demand, throttled to once a minute. `selfupdate.Updater.Start` downloads and sha256-verifies that release's `krill-linux-<arch>` binary against its own `checksums.txt`, smoke-tests it with `--version` and an empty environment, keeps the running binary as `<bin>.prev` (a hard link, so there is never a moment with no binary at all), writes a `10-krill-update.conf` drop-in (`StartLimitIntervalSec=0`, so a crash-looping new binary keeps restarting instead of landing in `failed`), arms a 10-minute `krill-update-revert` transient timer, and asks systemd to restart the unit from a separate `krill-update-restart` transient unit — never `systemctl restart` directly, which would run inside `krill.service`'s own cgroup and be SIGTERMed by the very stop it requested. Coordination between the old and new process runs through marker files in `/run` (`krill-update-pending`/`-reverted`/`-rolledback`, cleared on reboot along with the transient timers they coordinate with): `Updater.ConfirmStartup`, called once the new process is serving, finds the pending marker, deletes it and cancels the revert timer — which is why a broken new binary that never gets that far is put back automatically. Whenever it reports a result (an update confirmed, interrupted or reverted, or a rollback completed), it also runs one `Checker.Check` in the background (`refreshLatest`, outside the job slot, skipped when `KRILL_UPDATE_CHECK_INTERVAL` is 0; `Check`, not `CheckNow`, so a failed lookup does not take the manual button's once-a-minute allowance), since the checker's state is in memory and its loop waits a minute before the first check — Updates used to say "not checked yet" for that minute right after an update. `server.StartupGate` answers a 503 "Krill is starting" page on the listener from the moment it opens (before migrations even run) until the router is swapped in, so the browser — and the Updates page's own poll — sees progress across the restart instead of a refused connection. `internal/server/update_handlers.go` + `templates/updates.templ` render the page and the install/rollback/status endpoints (`RequireInstanceAdmin`); `cmd/krill/selfupdate.go`'s `updateBusy` refuses to restart while a deploy, a backup/restore or a DB-instance node move is in flight — asked when the request arrives and again by the job itself right before it changes anything on the host (after the download and smoke test; before the swap for a rollback), failing the job with a `*selfupdate.BusyError` if work started meanwhile. `Previous`/`Rollback` only offer a `<bin>.prev` whose version is a release strictly older than the running one, and `install.sh` deletes `krill.prev` whenever it installs a binary, since an old one may be several releases behind. Offered only to a release build (`buildinfo.IsRelease`) — a `git describe` build from source is a semver prerelease and never "newer" than anything. The whole mechanism only works because migrations stay additive across a release ([the migration compatibility policy](code-map.md#migrations-must-keep-the-previous-release-bootable-expandcontract), checked by squawk via `make lint-migrations` in CI and read by reviewers): a binary rolled back after a failed update must still be able to start against whatever schema the newer one already applied, which `database.RunMigrations` allows by skipping `Up()` (with a warning) when the recorded version is ahead of what it embeds.

## Krill state backup

*(2026-11-20)*

`internal/statebackup` (`dsn.go` DSN parsing and libpq env, `object.go` key layout and retention, `settings.go`, `store.go`, `service.go` the run) dumps Krill's own database with `pg_dump` and streams gzip → age (X25519 recipient only) → S3 (`internal/backup` transport, through the SSRF guard) with a size check. The dump runs in a one-off sidecar (`docker.OneOffRunner`, `internal/docker/oneoff.go`) on the host network, image `postgres:<server major>-alpine`, labelled `krill.role=state-dump`; every other connection parameter is a libpq env var, but the DSN password (`ConnEnv.Password`) reaches it only on stdin (`OneOffSpec.Stdin`, over the attach stream): the container's Env is part of its create request and config, which `docker inspect` and a debug-level daemon log show. Its command is `dumpCmd(nonce)` — a POSIX `sh -c` wrapper (`dumpScript`) that reads the first stdin line, exports `PGPASSWORD` only when it is non-empty, runs `pg_dump` with `DumpArgs()` and, only after it exited 0, prints `\n-- krill-state-backup-complete <nonce>\n` with a random per-run nonce (argv; not secret); a password with a line break is refused (`ErrPasswordLF`). `markerTail` holds back the last `len(marker)` bytes so the marker never reaches the archive, and a run whose stream does not end with exactly that marker fails before age is finished (`errIncompleteDump`, no object) — this replaced a "pg_dump footer in the last 1 KiB" check, which SQL containing the footer line could satisfy. `DumpArgs()` excludes the *data* of `*.sessions` and `*.metric_samples`. `verify-full`/`verify-ca` DSNs without `sslrootcert` use the host's CA bundle; relative SSL paths and unix-socket DSNs are refused. Keys: `<prefix>/krill-state/<ts>.sql.gz.age` (retention: keep N) and `<prefix>/krill-state/pre-update/<ts>_<from>_to_<to>.sql.gz.age` (keep 5, `PreUpdateKeep`); retention deletes only keys matching the exact pattern of their directory. One run slot serializes manual, scheduled and pre-update runs (a duplicate gets an error flash / INFO skip / `BusyError`); the startup sweep of leftover sidecars holds the same slot. `state_backup_settings` is a `panel_gateway`-style singleton (secret key `secret.Enc`, reused only for the same scheme/host/port; Save checks `HeadBucket` and refuses on failure); `state_backup_runs` is a 30-day journal that always keeps the newest successful run. Rulings: **Back up now** works while paused when storage and the recipient are set (`Settings.Ready()`), pause stops scheduled and pre-update runs (`Configured()` = enabled and ready); schedule "off" = on demand only (manual and pre-update still run).

**Pre-update hook:** `selfupdate.Updater.install()` calls `SetSnapshot`'s function first (phase `PhaseBackingUp` = `backing_up`, `jobTimeout` 25m, snapshot 10m) and a failure aborts the update with a `SnapshotError`; the escape hatch is pause, update, resume; `updateBusy` counts a running state backup as `state_backup` (the update's own snapshot takes no busy flag). Alerts (`internal/notify/statebackup.go`) go only to channels with `notify_infra` on; the digest gets a "Krill state" block (yellow when not set up, paused or a scheduled backup is overdue — cron in the host's local zone, 1h grace; red on failure; neutral on demand). Page: `internal/server/statebackup_handlers.go` + `templates/state_backup.templ`, `/orgs/{id}/krill-backups`, `RequireInstanceAdmin`; wiring in `cmd/krill/statebackup.go`. **Restore is by runbook only** (`docs/install.md`, no UI/button): it restores configuration, not workloads, and a logical database's user/database must be recreated by hand on a redeployed instance (ROADMAP follow-up). No new env var. See `docs/guides/krill-backups.md`.

## Observability agent

an opt-in Grafana Alloy agent (`internal/observability`) ships host metrics (Prometheus remote write) and every container's Docker logs (Loki) from every node to storage the operator provides — Krill stores only the two push addresses and their credentials (`observability_settings`, migration 000047, a `panel_gateway`-style singleton row), never the collected data itself. `Reconcile` converges a single **global** Swarm service, `krill-alloy-node`, from the saved settings via `docker.SwarmObjects` (`ConfigEnsure`/`SecretEnsure`/`PruneObjects`, the optional capability only the real engine implements): the rendered Alloy config and each target's password become configs/secrets named after a hash of their own content (`krill-alloy-node-<hash8>`, `krill-alloy-metrics-password-<hash8>`, `krill-alloy-logs-password-<hash8>`), labelled `krill.observability=node-agent` — a changed setting is a new object plus a rolling update, never an in-place edit, and nothing secret sits in the service spec; old objects are pruned once no running service references them (an in-use one is skipped and caught by the next pass). The service deploys **stop-first**, not Krill's usual start-first roll: two agent tasks on one node would fight over the same WAL volume (`krill-alloy-node-data`). Settings → Observability's **Check** button posts one throwaway metrics sample and log line through `client_golang/exp`'s remote-write client, which has six sharp edges worth remembering when touching `internal/observability/check.go`: it only speaks Remote Write 2.0 (so a v1-only receiver's `415` counts as success, since the agent itself sends 1.0 via Alloy's `protobuf_message = "prometheus.WriteRequest"`); it reports the HTTP status only inside its own error text (hence the `recordingTransport` wrapper that captures it independently); it wraps connection errors in a type with no `Unwrap`, so `errors.Is` on the returned error fails and the same `recordingTransport` is what actually records the underlying error; `remote.BackoffConfig{MaxRetries: 0}` means *retry forever*, not *don't retry*; `remote.NewAPI` appends `api/v1/write` to the given URL unless called with `remote.WithAPIPath("")` (the stored URL is already the full push URL, as Alloy expects it); and the client itself treats a 2xx response with no `X-Prometheus-Remote-Write-*-Written` headers as an error, which `classify` has to recognize and report back as `obs.check.ok_unconfirmed`, not a failure. A failed check never blocks turning the agent on. The reconciler loads its settings through `LoadForReconcile`, not `Load`: a disabled row reads as the zero `Settings` without decrypting anything, so after a `KRILL_SECRET_KEY` rotation "Turn off" (and the startup pass) still tears the agent down instead of failing on an undecryptable password; `Check` and enabling keep using `Load`. A stored password is bound to its server: `Save` keeps it on an empty password field only while the new URL has the same scheme, host and effective port as the stored one (a path change is fine), and otherwise refuses with `ErrPasswordRequired` (`flash.err.obs_password_required`) so the old credential never goes to another host. `Reconcile` honors `NetworkEnsure`'s `created` flag like `traefik.Reconcile` — a recreated base network forces a redeploy even with a matching spec hash. Handlers: `internal/server/observability_handlers.go`; template: `templates/observability.templ`; wired in `cmd/krill/main.go` behind a type-assertion on `observability.Engine` (`docker.SwarmObjects` + the existing service methods), so an engine that can't manage Swarm configs/secrets leaves the page present but unwired. `krill_node` on every metric and log line comes from `node_labels` (the Nodes page's names), falling back to the raw Swarm hostname for an unlabelled node; the per-node relabel rules match on a `__tmp_krill_node` snapshot label that is explicitly `labeldrop`ped before `remote_write`/`loki.write`, since `prometheus.relabel` relabels samples (not scrape targets) and does not strip `__`-prefixed labels on its own the way target relabeling would. `setNodeLabel`/`removeNode` (`internal/server/node_handlers.go`) call the reconciler's `Trigger()` — a non-obvious link, since renaming or removing a node changes the rendered config's object hash and so redeploys the Swarm service — while `addNode` deliberately does not, since an unlabelled node changes nothing; clearing an already-configured target's address also requires an explicit confirmation checkbox (`TargetInput.Clear`, `ErrClearNotConfirmed`/`ErrClearWithAddress`) rather than saving a blank field silently. `Reconcile` returns a `Coverage{Expected,Deployed,Missing}` alongside its error: a node Krill still expects a container on (anything not drained) that never received the current config is named on the settings page as still on the previous settings — a report of the LAST completed pass, refreshed only by the next one (a settings save, enable/disable, a node rename/remove, or a restart), not a live status.

## App metrics (observability stage 2)

`internal/appmetrics` owns endpoint and token rules. Migration `000048_app_metrics` adds `applications.metrics_enabled`, encrypted `metrics_token`, `metrics_token_env`, and `app_metrics_endpoints`. Organization admins configure the Metrics tab; members can see endpoints/status but never the token. `deploy.DBStore.applyMetrics` injects the token after env_text and DB links. Its hash is a **container** label (`krill.metrics-token-hash`), not a service label: `syncAppLabels` rewrites service labels on domain edits and now also excludes metrics paths. TCP port publication and token-variable collisions are checked in both directions, including API SetEnv. `krill-alloy-apps` runs one task on a manager with all organization networks; `TriggerNetworks` applies a one-minute cooldown. The quiet access-log provider `/_krill/alloy/apps` uses a third HMAC token from the gateway secret, refuses gateway requests, and serves a secret Alloy module. DNS task addresses are kept only when mapped to nodes on the app's organization network. Docker capabilities remain optional interfaces. `ReadAppsStatus` reads the collector's loopback API with bash `/dev/tcp` via Engine.Exec; fixture JSON comes from Alloy v1.19.2. See `docs/guides/metrics.md`.

## Notifications

*(Phase 7)*

`internal/notify` sends Telegram alerts on failures + health transitions (deploy failed, backup failed, app down/recovered — no success spam). Org-scoped `notification_channels` (bot token encrypted via `secret`, masked in UI, never logged). Sources push events through tiny consumer-side interfaces (`deploy.Notifier` in `finish()`, `backup.Notifier` in `fail()`); a background `notify.Watcher` polls `ServiceStates` every `KRILL_HEALTH_POLL_INTERVAL` and alerts on healthy→down (debounce 2) / down→healthy transitions (in-memory state keyed by `watchKey{db, id}`, since apps and DB instances have independent id sequences; a service never seen healthy stays silent — that case is covered by deploy-failure). It watches **DB instances too** (`ListWatchedDBInstances`, `DBDown`/`DBRecovered`, health category, 2026-11-21): a powered-off node left a pinned Postgres with a pending, unplaceable task for 4.5 h and nothing alerted, because only apps were watched and the apps kept running. A `migrating` instance, one whose `oplock.DBInstance(app_name)` is held (a node move, a deploy, a backup) and one scaled to 0 are intentional and stay silent. While such an operation holds it, the instance is skipped outright (streak reset, an outstanding alert kept), not treated as stopped. An instance recorded `running` counts as seen healthy on the first pass after startup (`primed`, so an outage already in progress when Krill restarts is reported) and, later, once its `updated_at` is `dbRunningGrace` (5m) old — a server that started and failed between two polls is still reported, a slow first start is not. Best-effort + async (detached ctx, 10s send timeout). Settings → Notifications (admin-only) + a "Send test message" button. See `docs/superpowers/specs/2026-06-07-krill-phase7-notifications-design.md`.

## Notifications beyond failures

*(2026-11-18)*

branch `notify-digest`; live acceptance in
ROADMAP (item 17). Migration 000061 adds channel columns (`notify_deploy_success`,
`notify_infra`, `disk_threshold_pct` 85, `mem_threshold_pct` 100, `digest_enabled`,

**Node data is operator-only:**
`notify_infra` and the thresholds are taken from the form only for `RequireInstanceAdmin`-
grade users (`auth.IsInstanceAdmin`); an org admin's save keeps them, and changing the
token or chat of an opted-in channel turns `notify_infra` off (`saveNotifications`). The
digest of a non-infra channel never contains node data. `deploy.Notifier.DeploySucceeded`
(only on `StatusRunning`, trigger `system` skipped) sends at once and queues a memory
check in `notify.ResourceMonitor`, a `metrics.Observer` fed by every sampler tick: the

under the threshold). The three backup services report `…Succeeded(id, size)`; notify
writes every run (ok and error) to `backup_runs` (pruned after 30 days) — successful
backups are reported only in the digest. `notify.Digest` ticks every minute, claims the LOCAL

while `(143): dockerexec: unhealthy container` stays a crash);
`ServiceStates` (same `notify.SwarmReader`) tells an app that should run from one stopped on purpose.
Digest and alert lines name what each number is (2026-11-19, `digest-wording`): "used"/"free"
(free = df's Avail from `node_disks.avail_bytes`, not total − used, so the root reserve is not

the node's level from `nodeFigures`, at most two plus "and N more"). Every node, app, deploy and backup line carries 🟢/🟡/🔴 (bands in `digest.go`, the channel's disk
and limits thresholds are the red marks; table in the guide). tzdata is

**Bot API replies (2026-11-19, v0.9.3 bug):** `sendMessage` echoes the whole message, so a
long digest's reply is several KiB; reading it through a 4 KiB `LimitReader` cut the JSON and a

## Structured log viewer

*(Phase 7)*

app + DB runtime logs render as a Dokploy-like table (time | level | message) instead of raw xterm. `ServiceLogs` requests docker `Timestamps`; `ParseLogLine` (`internal/logparse`, unit-tested — moved out of `internal/server` so `internal/api.AppLogs` can share it) strips the docker RFC3339 prefix and detects the level (logfmt `level=` or a leading INFO/WARN/ERROR/DEBUG/TRACE/FATAL/SUCCESS token); `streamParsedLogsToWS` sends `{t,lvl,msg}` JSON frames. Swarm applies `tail` to each task separately and interleaves tasks in arbitrary order (a task stopped days ago could land below the running one — seen live after v0.13.0), so `Server.streamServiceLogsToWS` first reads a non-following stream and sends its newest 200 non-blank lines merged by docker timestamp (`logparse.Backlog`: a min-heap with a 4 MiB text budget, never the whole stream), opens the follow stream with a 50-line per-task overlap right after that read (before sending anything, so a slow browser does not widen the gap), and drops replays with `logparse.Cursor`. The cursor keeps its place **per Swarm task**, because tasks on different nodes have unrelated clocks: `docker.Engine.ServiceLogs` requests log `details`, and `logparse.ParseLogLine` strips them into `LogLine.Task` (the API's `AppLogs` gets the same stripped lines). A task whose first following line is already new wrote more than the overlap in between, or its backlog was cut before its end: the viewer gets the `log.gap` notice before it. Old tasks' lines stay, in time order (as `api.AppLogs` returns them). Since v0.13.3 the backlog read is bounded, opening included (`logparse.ReadBacklog`/`ReadWithin`, `logparse.BacklogTimeout` = 10s, also used by `api.AppLogs`; the context handed to the engine is cancelled when the read returns): what was read is used, and an incomplete backlog (cut by the bound, or a stream ending with `logparse.ErrIncomplete` because the engine could not read a task) gets the `log.cut` notice (`api.AppLogs`: a warn line). The backlog waits at most `followOpenWait` (5s) for the following stream to open before it is sent, then the server sends `{"ev":"live"}` and the client shows `log.waiting` while no timestamped line has arrived (a placeholder row that filters never hide), instead of a blank pane (see [A non-following service log read can stall](#a-non-following-service-log-read-can-stall)). The client island `mountLogViewer` (`[data-logs]`) renders color-coded rows with text search + a level filter (all or one level). Deploy/build logs (`DeployLogHub`, `.term[data-term-log]`) and the interactive Terminal (`.term[data-term-ws]`) still use xterm. See `docs/superpowers/specs/2026-06-08-krill-phase7-log-viewer-design.md`.

## Web terminal

*(Phase 7)*

admin-only interactive `docker exec` into a running app container via xterm + WebSocket. `docker.ExecInteractive` returns an `ExecSession` (TTY, raw stream); the admin-gated `appTerminal` WS handler runs `pumpTerminal` (binary frames = stdin, text frames = `{"rows","cols"}` resize, session output = binary back), with `KRILL_TERMINAL_IDLE_TIMEOUT` reaping idle sessions. Tenancy via `loadAppCtx`; session I/O is never logged; same-origin WS. Terminal tab on the app page (`/bin/sh` + command override). The live `docker exec` path is verified on a real host (no Swarm in unit tests). See `docs/superpowers/specs/2026-06-07-krill-phase7-web-terminal-design.md`.

## Logging

structured `slog`, configured in `cmd/krill/main.go` (`setupLogging`). One access-log line per request comes from the `requestLogger` middleware (`internal/server/logging.go`); 5xx logs at error level. In handlers use `logFrom(r)` — a `*slog.Logger` pre-tagged with `request_id`/`user_id`/`org_id` — for error logs (before any 5xx response) and INFO audit logs (before the success redirect). Never log secrets (passwords, temp passwords, tokens, connection strings).

## Release, image and installer

- **`Dockerfile`** — multi-stage: `golang:1.26.11-alpine` builder (`--platform=$BUILDPLATFORM`, cross-compiling with `GOOS=$TARGETOS GOARCH=$TARGETARCH`, so the arm64 image never runs Go under QEMU) → `CGO_ENABLED=0` static binary → `gcr.io/distroless/static-debian12:nonroot` (~25 MB, runs as UID 65532). It relies on the COMMITTED generated files (no `make generate` in-image); migrations (`//go:embed migrations/*.sql`) and static assets (`//go:embed all:static`) are embedded, so the final image is binary-only. Build locally: `docker build -t krill:local .`.
- **`.github/workflows/ci.yml`** — push (all branches) + PR: build/vet/test (testcontainers works on the runner's native Docker — do NOT add the Colima socket override here), a no-push Docker build, and a generated-drift check (`make generate` + `git diff --exit-code`).
- **`.github/workflows/release.yml`** — `v*.*.*` tag (or `workflow_dispatch`): multi-arch buildx → push to `ghcr.io/${{ github.repository_owner }}/krill` → GitHub Release on tag pushes. On a tag it ALSO cross-compiles static binaries (`krill-linux-amd64`/`krill-linux-arm64`, `CGO_ENABLED=0`, committed generated files) + a `checksums.txt` and attaches them as Release assets — these are what `install.sh` downloads. Both the binaries and the image are stamped with the same version: `-X github.com/proshik/krill/internal/buildinfo.Version=<tag>` on the Go builds, `VERSION=<tag>` as the Docker build-arg — `krill --version` reports the release tag either way. Uses `GITHUB_TOKEN`; needs `permissions: packages: write` + `contents: write`. A package published from this public repository comes out public: `ghcr.io/proshik/krill` pulled anonymously right after v0.1.0, with image tags `0.1.0`, `0.1`, `latest` and `sha-<commit>` (no leading `v`).
- **`install.sh`** (repo root) — VPS one-liner (`curl -sSL …/master/install.sh | sudo sh`): host binary + systemd (NOT a container), idempotent (re-run = upgrade). Installs Docker if missing → `swarm init` → loopback-only `krill-postgres` container for state, on its own `krill-state` Docker network rather than the default bridge (a build container also sits on the default bridge and could otherwise reach Postgres by IP even with the loopback-only port publish; an upgrade from an older install removes and recreates the container to move it — same volume, same data) → downloads the checksum-verified release binary (fail-closed: missing `checksums.txt`/entry aborts unless `KRILL_SKIP_VERIFY=1`) → generates `/etc/krill/krill.env` (admin pw + `KRILL_SECRET_KEY` created once, preserved on re-run; `KRILL_COOKIE_SECURE=false` — it stays false; the UI gets HTTPS from **Settings → Panel domain**, not from this flag) → `krill.service` (`StartLimitIntervalSec=0`, so a fast-failing unit — Postgres not up yet after a reboot, a broken upgrade — keeps retrying instead of landing in `failed`; the self-update drop-in sets the same thing for a unit installed before this). Variant A (host binary) was chosen over a Swarm-service install to avoid the nonroot-socket and self-exposure chicken-and-egg. See `docs/superpowers/specs/2026-06-09-krill-installer-design.md`.
- After changing the build/embed setup, re-verify by actually building the image (`docker build .`) and confirming it still runs (`docker run --rm krill:local` should fail fast on the missing `KRILL_DATABASE_URL`).

## Pitfalls

### A table holding a live bearer credential in plain form must be added to `DumpArgs()`'s `--exclude-table-data` list

**A table holding a live bearer credential in plain form must be added to `DumpArgs()`'s `--exclude-table-data` list** (`internal/statebackup`). Today that is `sessions`; a new table like it (login tokens, one-time links) would otherwise put working credentials into every state backup. `metric_samples` is excluded for size.

### State-dump sidecars (`krill.role=state-dump`) get the DSN password on stdin, never in Env, argv or labels

*(2026-11-21)*

Docker's debug request logger records a container-create body (Env included), and `docker inspect` shows Env, so `OneOffSpec.Env` must never carry a secret; `OneOffSpec.Stdin` goes over the hijacked attach stream, and `cancelConn` forwards `CloseWrite` so the stream can end the container's stdin (without it `HijackedResponse.CloseWrite` is a silent no-op). Inside the container the wrapper exports `PGPASSWORD` to pg_dump's process only. The run is accepted only when the stream ends with exactly the per-run completion marker the wrapper prints after `pg_dump` exited 0. Sidecars are still removed on exit and any leftover at startup (a running one's pg_dump holds the password in its process environment).

### A non-following service log read can stall

*(2026-11-24, v0.13.3)*

`docker service logs` without `-f` over several tasks stopped mid-stream and never ended once the tails were large (a three-node production cluster on Docker 29.1.3, two apps with five tasks each; reproduced on a two-node docker:28-dind Swarm with five tasks of ~1.2 KB lines and `--tail 200`: 6/6 reads stalled after 335–523 of 600 lines, while `--tail 20`, small lines, and every single-task read always ended). Swarmkit's worker answers one subscription with one goroutine per task, all calling `Send` on the same gRPC stream (`agent/worker.go` Subscribe + `agent/agent.go` Publisher), which gRPC does not allow. `dockerEngine.ServiceLogs` with `follow=false` therefore lists the service's tasks (`logTasks`: skips tasks without a node and tasks whose container has not started; keeps `starting` ones — during a start-first update their container logs while the healthcheck is pending, and Swarm's own read showed those lines; running ones first, then newest) and reads them one by one through `TaskLogs`, each capped by `taskLogTimeout` (5s); a task that fails or times out is skipped and the stream then ends with `logparse.ErrIncomplete` after the other tasks' lines — `TestServiceLogsBacklogEndsWithEveryTask` (`-tags=integration`, `KRILL_IT_CONSTRAINT=node.role==worker` against a multi-node Swarm) fails on the old read. The following stream is still one subscription and can lose part of its initial tail burst the same way (live lines keep coming); callers bound the backlog anyway (`logparse.BacklogTimeout`).

### A long-lived non-WebSocket response holds `http.Server.Shutdown` until its deadline

*(2026-11-16)*

Shutdown waits for every active connection but not for hijacked ones, so the UI's WebSockets (logs, terminal) never held a stop — an MCP client's standalone `GET /mcp` stream did: the go-sdk keeps it open until the request context ends or the session closes, so every self-update with an agent connected ended in `fatal: context deadline exceeded`, exit 1 and systemd's `Failed with result 'exit-code'`. `Server.StopStreams` (registered with `srv.RegisterOnShutdown`) cancels the context of `GET /mcp` via `endStreamOnShutdown`; mount any new streaming GET (SSE, long-poll) behind the same middleware. A stop that still runs out of `shutdownBudget` (10s, well under systemd's default 90s `TimeoutStopSec`) is not a failure: `gracefulShutdown` (`cmd/krill/shutdown.go`) logs a WARN listing the requests still in flight (`server.Inflight`, method + path only, wired through `ConnContext`/`ConnState`: a request stays listed until its connection goes idle, closes or is hijacked — net/http keeps a connection active after the handler returns while it drains an unread body, and stops waiting for it once hijacked), closes them with `srv.Close`, and `run()` returns nil — exit 0, `Deactivated successfully`. Real failures (startup, `Serve`) still exit 1, which `Restart=always` restarts the same way.

### Never restart `krill.service` from inside its own cgroup

A child of the process (e.g. a `firewall.LocalRunner` command) running `systemctl restart krill` would itself be a member of `krill.service`'s cgroup, and the stop half of the restart (`KillMode=control-group`) SIGTERMs it along with the parent — reporting "signal: terminated" for a restart that is actually in progress. `selfupdate.Updater.restartCmd` instead schedules a transient `systemd-run` unit two seconds out to run the `systemctl restart`, from outside the cgroup entirely.

### systemd's default start-rate limit (5 starts in 10s) parks a fast-failing unit in `failed`

**systemd's default start-rate limit (5 starts in 10s) parks a fast-failing unit in `failed`**, and `Restart=always` stops applying — hit by a crash-looping post-update binary, or by Postgres still starting after a reboot. Both `install.sh`'s unit and the self-update drop-in (`10-krill-update.conf`) set `StartLimitIntervalSec=0` so the unit just keeps retrying instead.

### The pending self-update marker is written before the binary is renamed into place, not after

Should the process die right between the two, the *new* binary starts, finds `krill-update-pending` and confirms itself instead of being reverted. Symmetrically, the revert script's first line is `[ -e $pending ] || exit 0` — `ConfirmStartup` deletes the marker before it cancels the revert timer, so a timer that still fires (a cancel that arrived too late) finds nothing to revert.

### A `git describe` version (`v0.1.3-6-g1a09ec0`, `v0.1.3-dirty`) is valid semver but a prerelease

**A `git describe` version (`v0.1.3-6-g1a09ec0`, `v0.1.3-dirty`) is valid semver but a prerelease**, so plain `semver.Compare` would rank it *older* than the release it descends from and "update" it backwards. `selfupdate.Newer`/`buildinfo.IsRelease` require the running binary's version to be a plain `vX.Y.Z` tag before it is ever offered an update — a `make build` or `go build` from a checkout never is.

### `alloy validate` does not catch expression errors

**`alloy validate` does not catch expression errors** — a misspelled component reference or field (e.g. `constants.hostname`) still validates as syntactically correct Alloy and only fails once the agent actually runs and evaluates it. It also accepts a lexically invalid string escape (e.g. `"host\.name"`, a single backslash before a non-special character) that `alloy run` then rejects at load with "unknown escape sequence" — so `validate` passing is no guarantee the file is even loadable, not just that it's semantically right. `internal/observability`'s config-rendering tests can't rely on `alloy validate` to catch either class of bug; only an integration test that runs the real agent does.

### App collector Alloy timings

`remote.http` uses `poll_frequency=30s` and `poll_timeout=10s` (timeout strictly less); scrapes use interval 30s and timeout 10s (timeout no greater). Use `job_name` rather than relabeling job. An initial unavailable or invalid imported module stops Alloy; failed subsequent polls keep the last module. A collector restart while Krill is unavailable therefore crash-loops until Krill returns. Every scrape carries `sample_limit`/`body_size_limit`/`label_limit`/`label_value_length_limit` so one tenant's endpoint fails alone instead of OOMing the shared collector (256 MiB — sized from a real-Alloy measurement: ~37 MiB empty, ~116 MiB at 25k series, ~157 MiB at 50k, see `docs/guides/metrics.md`); `body_size_limit` must be a unit string (`"5MiB"`) — Alloy's docs call it `int`, but a bare number stops the collector at load ("unknown unit"), which only `TestAppsCollectorEndToEnd` on the real agent catches.
