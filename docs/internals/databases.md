# Managed databases, buckets and backups

DB instances and logical databases, the per-engine drivers, app links, S3 buckets, and the backup engine for databases.

## DB instances

*(2026-07)*

the one-container-per-database managed-DB model is gone, replaced by org-level `db_instances` (Postgres/Redis servers, one Swarm service per instance, optionally pinned to a node) + env-scoped `logical_databases` living inside a Postgres instance. Creating a logical DB provisions it synchronously via `Engine.Exec` piping SQL into `psql` on stdin inside the instance's container — `CREATE USER`/`CREATE DATABASE ... OWNER ...`/`REVOKE CONNECT ON DATABASE ... FROM PUBLIC` (`internal/dbservice/provision.go`; full drop-compensation on any mid-way failure so a retry is safe). Redis instances still serve apps directly — no logical sub-resource, one instance = one connection target. `app_db_links` now points at real FKs (`logical_database_id` XOR `instance_id`, CHECK-enforced) instead of a loose `engine`+`db_id` pair, and `backups` target `logical_database_id` with a per-database S3 layout (`<prefix>/<app_name>/<db_name>/<ts>.sql.gz`, one directory per logical database so retention never mixes dumps from different databases in the same instance). Migrations `000029` (create `db_instances`/`logical_databases`, convert every legacy `postgres_dbs`/`redis_dbs` row into an instance in place — collision-safe across engines, no container recreation, existing volumes/services keep running) and `000030` (drop the legacy `postgres_dbs`/`redis_dbs` tables + the transitional `legacy_*`/`engine`/`db_id`/`postgres_db_id` columns) are both in. Changing a DB instance's node now migrates its data volume (stop→stream→redeploy on the target node, fail-safe rollback to the source on any error; capped by `KRILL_MIGRATE_TIMEOUT`; `MigrateInstanceNode` takes the instance lock before returning, so a duplicate gets `ErrInstanceBusy` rather than a false "migration failed" alert, and `DeployInstance` returns `ErrDeployInProgress` instead of silently dropping a second deploy) (code-complete; live cluster acceptance pending — see ROADMAP acceptance queue). UI: an org-level Database Servers page (`/orgs/{id}/db-servers` — create/deploy/start/stop/version/node/delete) + reworked environment Databases tabs (create/detail/delete/backups, now under `/projects/{p}/environments/{e}/databases`). See `docs/superpowers/specs/2026-07-02-krill-db-instances-design.md` and `docs/superpowers/plans/2026-07-02-krill-db-instances.md`.

## Stateful services — engine drivers

*(MinIO + DragonFly, 2026-07-08)*

managed engines are now **driver-based**. Per-engine knowledge (image/spec/args/env/mounts/health, external-access ports, app-link fields, connection display) lives in a leaf package `internal/dbservice/drivers` (imports docker+secret only, so both `dbservice` and `deploy` depend on it with no cycle): a `Driver` per engine registered in `drivers.Registry` (`postgres`/`redis`/`dragonfly`/`minio`), with `dbservice.Instance` a type-alias of `drivers.Instance`. The old switch/if engine special-cases collapsed into driver dispatch — `instanceSpec`→`Driver.BuildSpec`, `reconcileProxy`→`Driver.ExternalTargets`, detail conn block→`Driver.ConnDisplay`, deploy-time app-link resolver→`drivers.LinkValue(engine, src, field)`; `Driver.HasLogicalResource()` gates logical-DB provisioning (postgres-only — `provision.go` unchanged). postgres/redis were refactored into drivers behavior-for-behavior (regression tests assert the specs are unchanged). **DragonFly** (`dragonflyDriver` embeds `redisDriver`): Redis-compatible (RESP), image `docker.dragonflydb.io/dragonflydb/dragonfly`, args `["dragonfly","--requirepass",pw]`, port 6379, superuser `default`; conn/link fields identical to redis, so an existing redis app-link works unchanged. **MinIO** (`minioDriver`): S3-compatible, image `drivers.MinIOImage` = `pgsty/silo:RELEASE.2026-10-26T00-00-00Z` since 2026-11-06 (Silo, the owner-chosen MinIO fork: multi-arch, anonymous Docker Hub pull, MinIO env/API, entrypoint maps `server`→`silo`, ships `mc` and `curl` but no `flock`; the earlier `quay.io/minio/minio` pin answers 401 to anonymous pulls, which is what broke every MinIO test; `internal/testutil.NewMinio` runs the same constant; UI label "S3 (Silo)"; existing instances keep their image), args `["server","/data","--console-address",":9001"]`, env `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` (root user is user-chosen at create, validated `^[a-zA-Z0-9]{3,63}$`; password generated), **two external ports** — S3 API 9000 + console 9001 — so `ExternalTargets` returns 2 targets and `reconcileProxy` (generalized from B2's one-socat-per-instance to N targets per `Suffix`) raises `krill-dbproxy-<id>` (S3) + `krill-dbproxy-<id>-console`; healthcheck omitted in v1. App-linking is **engine-aware**: `app_db_links.field` CHECK (migration 000037) adds S3 fields `endpoint`/`access_key`/`secret_key`/`region` alongside the pg/redis-shaped set; the add-form's `db_ref` uses kind `pg:<logical_db_id>` (postgres, via logical DB) or `inst:<instance_id>` (any non-postgres instance — redis/dragonfly/minio), the Field `<select>` filters options by the target engine (JS `data-engine`/`data-engines`, server-validated against `Driver.LinkFields()`), and `drivers.LinkValue` resolves minio to `endpoint=http://<app>:9000` / `access_key=<root user>` / `secret_key=<pw via secret.Dec>` / `region=us-east-1`. **Instance-only in v1** (no env-scoped buckets/indexes — the app creates its own); no backups for the non-pg engines (backups stay `logical_database_id`-scoped, i.e. postgres-only). Three additive migrations: `000035` (`db_instances.console_external_port` + partial unique index), `000036` (recreate the engine CHECK allowing `postgres|redis|dragonfly|minio`), `000037` (`app_db_links_field_chk` + S3 fields). Deferred: OpenSearch (host `vm.max_map_count`/JVM-heap too heavy for the 1.9 GB VPS — same driver later), env-scoped sub-resources (buckets/indices → a future `logical_resources`), a Traefik domain for the MinIO console, and MinIO/DragonFly backups (incl. managed-MinIO as a Krill S3 destination). See `docs/superpowers/specs/2026-07-08-krill-stateful-services-minio-dragonfly-design.md` / `docs/superpowers/plans/2026-07-08-krill-stateful-services-minio-dragonfly.md`.

**Valkey (2026-11-06):** `valkeyDriver` embeds `redisDriver` (same RESP links/conn display, `redis://default:pw@app:6379`) but is its own engine (migration 000056 widens the engine CHECK): image `valkey/valkey:8.1.4`, args `valkey-server --requirepass pw --appendonly yes` (durable on `/data`), flock-wrapped `docker-entrypoint.sh`, stop-first, healthcheck `valkey-cli ping` with the password in `REDISCLI_AUTH` (valkey-cli 8 reads that, NOT `VALKEYCLI_AUTH`). The image's entrypoint drops to the `valkey` user only for `valkey-server`; it ships a `redis-server` link, so the redis driver's args would run it as root — never reuse the redis driver with a valkey image. `TestValkeyDriverOnRealImage` (`-tags=integration`) checks user, health, AOF persistence and the lock on both the Debian and alpine tags.

**Unknown engines (same date):** acting paths use `drivers.Registry.Lookup` (error), never `MustGet` (nil → panic in the deploy goroutine, which killed the process on v0.5.0/v0.6.0 for any engine they don't know — including `valkey` after a rollback, documented in `docs/install.md`).

**Single-writer protection (2026-09-18):** every driver's `BuildSpec` now sets `docker.ServiceSpec.UpdateStopFirst: true` (a live cluster caught two Postgres postmasters on one `PGDATA` during a worker-node return — both running for ~0.3s, then the new one serving for a further ~60s on a directory the old one had already shut down, until Postgres's own once-a-minute lock-file recheck killed it; the next start came up from the old one's `pg_control`, so anything written in that minute would have been silently lost); postgres/redis/dragonfly additionally wrap their `Command` in a portable `sh -c 'exec 9<"$0" && flock 9 && exec <entrypoint> "$@"' <MountTarget()>` to lock the volume's own mount-point directory against a second container appearing outside a service update too (a node returning mid-reconciliation is not one) — NOT `flock --no-fork`, which busybox (every alpine-tagged image) doesn't support. MinIO's image has no `flock`, so it keeps stop-first only — see [Two processes on one managed-DB data directory](#two-processes-on-one-managed-db-data-directory) and [Nodes](../architecture.md#nodes).

## DB→app linking

`app_db_links` table (migration 000019, rewired onto real FKs by 000029) links an app to a database → injects the live internal connection string into a chosen env var on **every** deploy (`internal/deploy/store.go` `resolveDBLinkURL`; overrides `env_text`; the password is pulled live via `secret.Dec`, never stored in `env_text`). Two kinds, chosen via the form's `db_ref=pg:<id>` / `db_ref=redis:<id>`: a **postgres** link points at a `logical_databases` row and is scoped to the app's own environment (`ld.EnvironmentID != c.Env.ID` → 404); a **redis** link points at a `db_instances` row directly (redis has no logical sub-resource) and is org-wide — any redis instance in the org can be linked, not just ones in the app's environment. UI: "Linked databases" section on the Environment tab (admin); links are cleaned up when the DB is deleted; IDOR/cross-org guard.

## Buckets

*(2026-11-06)*

env-scoped `s3_buckets` on an org-level S3 instance (engine `minio`) + `app_bucket_links` (migration 000057, new tables only). Managed with `mc --json` run through `Engine.Exec` inside the instance's own container (`internal/dbservice/s3.go`; the Silo image ships mc; owner chose this over an own admin-API client — madmin-go is AGPL), root creds in `MC_HOST_k` env, never argv. **`Engine.Exec`'s non-zero-exit error embeds the whole argv** — `mc admin user add` carries the new secret there, so `mcAs` never wraps an "exited" error (`TestMCFailureNeverCarriesTheSecret`); it parses mc's JSON status instead. A bucket gets policy `krill-bucket-<name>` (s3:* on that bucket only) and a user `krill-<name>-<6hex>`; import adopts an existing bucket + key after a write/read/delete probe; rotation keeps `prev_access_key` until an explicit revoke; delete refuses while linked, keeps objects unless `destroy_data`, removes only users Krill generated (`access_key_generated`/`prev_access_key_generated`, recorded on the row — never inferred from the name; rotation is a conditional update that only applies while no previous key is pending); env delete keeps bucket data and removes generated users; rotate/revoke/delete/link are serialized per bucket (`oplock.Bucket`), and `lockBucket` re-reads the row under the lock (a bucket gone meanwhile is a 404 with nothing changed on the server) so a mutation never acts on keys loaded before a rotation; import probes with a random, checked-free object name and reads it back; a restore that cannot start removes its new target only via `RemoveEmptyBucket` (`mc rb` without `--force`); `ListObjects` streams the listing and stops at `bucketbackup.MaxObjects` (200,000); an instance with buckets cannot be deleted. Links inject endpoint/bucket/access_key/secret_key/region (`DBStore.applyBucketLinks`), never root creds; `Dependencies` gains a `/b<hash>` part only when an app has bucket links (release identity of other apps unchanged); API ListEnv source `bucket-link`; `linkVarTaken` refuses a var used by env_text, the metrics token or a link of either kind. `TestBucketLifecycleOnSilo` (`-tags=integration`) proves restriction (another bucket → denied), import, rotation and revoke on the real image.

**Bucket backups (same date):** `bucket_backups` (migration 000059) + `internal/bucketbackup`: a snapshot copies every object (`mc ls --recursive --json`, then `mc cat` per object streamed through Krill into the backup storage with a running sha256) under `<prefix>/<server>/<bucket>/<ts>/objects/`, then writes `manifest.json` LAST — its presence is what marks a snapshot complete; retention counts complete snapshots only and drops half-written ones older than the newest complete. Restore is into a NEW, empty bucket only (the owner's choice; the handler creates it via `newKrillBucket` after checking the snapshot exists, and removes it again if the restore is refused — under the target's `oplock.Bucket`, only while nothing links to it and it is still empty; a destination's storage identity is host + effective port, so `https://h` and `https://h:443` are the same storage), verifying each object's sha256 and the final listing. `SafeKey` rejects manifest keys with `..`/empty/`.` segments or a leading slash: the manifest is read from storage anyone with its credentials can edit, and mc runs with the server's root credentials, so `k/<target>/../other/x` would write into another bucket. Third cron scheduler in `main.go`; counted as "backup" in the self-update busy check. **Failure alerts resolve their owner through the backup kind's own table** (`notify.Service.BackupFailed`/`VolumeBackupFailed`/`BucketBackupFailed`): the three tables have independent id sequences, and passing a volume or bucket backup id to the DB-backup lookup alerted whichever organization owned the DB backup with that number (pre-existing for volumes, fixed with this). `TestBucketBackupAndRestoreOnSilo` (`-tags=integration`) round-trips binary and spaced keys on the real image. See `docs/guides/buckets.md`.

## Backups/S3

*(Phase 4)*

`destinations` (org-scoped S3 config: endpoint/bucket/region/keys, plaintext) + `backups` (per-logical-database, `logical_database_id` FK: cron schedule, retention N, prefix, enabled, last_run/status — see [DB instances](#db-instances) below for the model). Dump path = `Engine.Exec` runs `pg_dump --clean --if-exists` inside the instance's container → gzip stream → S3 (aws-sdk-go-v2, path-style for MinIO) at `<prefix>/<app_name>/<db_name>/<ts>.sql.gz`; retention keeps newest N (count-based) per logical-database directory. Restore streams S3 → gunzip → `psql`. In-process `robfig/cron/v3` scheduler (`Scheduler.Reload` after any backup mutation, wired in main + via `Server.SetBackups`). `internal/backup` (s3.go/service.go/store.go/scheduler.go); destinations org-scoped + backups chain-checked (IDOR tests). S3 tested against a MinIO testcontainer (`testutil.NewMinio`); the live `pg_dump`/restore exec path is verified on a real host (no Swarm in unit tests). `runBackupNow`/`restoreBackup` run async on a detached context, started through `StartBackup`/`StartRestore` (and `StartVolumeBackup`/`StartRestore` for volumes), which claim the config's in-flight slot before returning — a duplicate gets `ErrBackupRunning` and an error flash instead of "started". Adding a second config with the same storage and prefix is refused: both would write to one S3 directory and each one's retention would delete the other's dumps. **UX simplification (2026-07-05):** the backup form now offers schedule **presets** (`backup.CronForPreset`/`SchedulePreset` — Off/Hourly/Daily/Weekly/Monthly/Custom) instead of a raw cron field; Off = empty schedule, which `Scheduler.Reload` skips registering (on-demand only — "Backup now" still works), friendlier labels ("Storage" for destination, "Keep last N backups" for retention, the S3 prefix under an "Advanced" disclosure, a state-aware Pause/Resume toggle), and an inline storage-creation form in the empty state (`createDestination` supports a `return` redirect back to the originating page). Engine unchanged — same S3 transport, same cron/retention semantics; DB and volume backups share the same form/terminology. See `docs/superpowers/specs/2026-07-05-krill-backup-ux-simplification-design.md` / `docs/superpowers/plans/2026-07-05-krill-backup-ux-simplification.md`. See [`ROADMAP.md`](../../ROADMAP.md) and `docs/superpowers/` for the full trail.

## Pitfalls

### Two processes on one managed-DB data directory

*(2026-09-18)*

A live cluster caught two Postgres postmasters on the same `PGDATA` during a worker-node return — the replacement task started before the old one (on the returning node) was confirmed gone. They overlapped for ~0.3s, but the damage window was a minute: the old one shut down cleanly (writing its shutdown point to `pg_control` and deleting `postmaster.pid`), the new one kept accepting connections on that directory for ~60s until Postgres's own once-a-minute lock-file recheck noticed the missing `postmaster.pid` and shut it down, and the next start recovered from the old one's `pg_control` — anything written through the new one in that minute would have been silently dropped. Postgres's own lock is therefore a late reaction, not a guard: had the old process crashed instead of stopping cleanly, the pid file would have stayed and nothing would have stopped the new one at all. Fixed two ways, together: (1) `UpdateStopFirst: true` on every DB driver's spec (`internal/dbservice/drivers`) closes it for a service-spec update. A DB instance has no Reload/Rebuild (that's an app-only concept, see **App lifecycle controls**); its own actions are Deploy, Start, Stop, a version (image) change, a node move, and delete — Deploy/version-change/node-move all redeploy the service through the shared `deployCore` and so pick up the new spec, and so does `ParkInstance` (the org-network migration's way of moving a *stopped* instance onto its network without starting it — `StartInstance` only scales, so a parked instance would otherwise come back up on the old network), but **Start/Stop are `ServiceScale` only and reuse whatever spec is already running** — see [Changing `UpdateConfig.Order` itself takes effect in the very rollout that changes it](deploy.md#changing-updateconfigorder-itself-takes-effect-in-the-very-rollout-that-changes-it-not-the-next-one) for why the very deploy that turns this on already rolls out stop-first; (2) each driver's `Command` wraps the container's own entrypoint in a *portable* flock, locking the volume's own mount-point directory (from `Driver.MountTarget()` — for Postgres the volume IS `PGDATA`, so the lock has to be the bare directory, not a file inside it, since `initdb` needs it empty on first start) — this is what closes a worker-node return, which is not a service update at all and `UpdateConfig.Order` cannot see. It is deliberately NOT `flock --no-fork`: busybox's `flock` — shipped by every alpine-tagged image, and the image is free text at create/version-change time (`postgres:16-alpine`, `redis:7-alpine`, ...) — has no `--no-fork` flag at all and fails outright ("flock: unrecognized option: no-fork"), which would crash-loop an alpine-based instance. Instead `Command` runs `sh -c 'exec 9<"$0" && flock 9 && exec <entrypoint> "$@"' <MountTarget()>`: opening the directory on a fixed fd and locking THAT FD (not a path) is understood by both util-linux's and busybox's `flock`, and per `flock(1)` the lock is not released when `flock` returns because the fd was already open on the command line — so it's held by the shell process itself through every later `exec` in the same process (the image's own privilege drop, then the real entrypoint) without needing to keep `flock` itself as PID 1. Postgres/Redis/DragonFly images ship both `sh` and `flock`; **MinIO's image has no `flock`**, so MinIO gets stop-first only, not the directory lock — recorded as an accepted gap, not fixed. A custom image missing either tool fails to start (missing `sh` surfaces as Docker's own "executable file not found"; missing `flock` surfaces as a shell error from inside the container, e.g. "flock: not found") — same tradeoff, recorded rather than special-cased. An existing instance is protected only once it goes through a Deploy, version change, or node move (whichever redeploys it with the new `Command`) — **a Start/Stop cycle does not**, so an instance that has only ever been started/stopped since this shipped is still exposed to a bad node return; Krill does not mass-redeploy every DB instance on upgrade, so redeploy instances holding real data right after upgrading Krill.

### Named volume `<appName>-data` persists

**Named volume `<appName>-data` persists** for managed databases unless the user opts in via the "Destroy data" checkbox (`destroy_data=on`) on delete; only then is `engine.VolumeRemove()` called. Removal retries (`dbservice.removeVolume`) because right after `ServiceRemove` the volume is briefly "in use" while Swarm tears down the task container. **Deleting an environment or project** (`internal/server/project_handlers.go`) removes its apps' services and Docker volumes (`removeEnvAppVolumes`), drops its logical Postgres databases with their data inside their servers (`removeEnvDatabases`) and removes the bucket users Krill generated (`removeEnvBuckets`); bucket contents, the database servers and their volumes stay. The confirmation texts (`envset.delete_hint`, `confirm.delete_project_more`) say exactly this — keep them in step with the handlers.

### DB log feeds use negative feed IDs to avoid colliding with positive deployment IDs

The `DeployLogHub` lives in `internal/deploy/logs.go`; the feed-ID helper lives in `internal/dbservice/instance.go`: `InstanceFeedID(id) = -id` — one instance table now (unlike the legacy pg/redis pair, which needed two disjoint formulas), used by the `dbInstanceDeployLogs` WS handler.
