# Agent API (MCP + REST)

The agent-facing API: operations, token auth, the MCP session binding, and provisioning.

## Agent API — MCP + REST

*(2026-08-13)*

twelve agent-facing operations over apps that **already exist** (plus four creating ones since 2026-11-21, see Provisioning below, and four diagnostic ones since 2026-11-26, see Diagnostics at the end), living in one transport-agnostic service layer (`internal/api`, tenancy + level gate inside) with two thin adapters: **REST** `/api/v1/*` (`internal/server/api_handlers.go`) for CI/scripts and **MCP** streamable HTTP at `/mcp` (`internal/mcpsrv`, `github.com/modelcontextprotocol/go-sdk` v1.8.0; its DNS rebinding guard is off via `DisableLocalhostProtection` — it would 403 a same-host reverse proxy forwarding a domain to 127.0.0.1, and the bearer token already rules out a rebound browser page). Read tools/routes: `krill_whoami`, `krill_list_apps`, `krill_app_status`, `krill_app_logs`, `krill_deployments`, `krill_deployment_status`, `krill_list_env` (`GET /api/v1/whoami|apps|apps/{app}|apps/{app}/logs|apps/{app}/deployments|deployments/{id}|apps/{app}/env`). Write: `krill_deploy`, `krill_rebuild`, `krill_reload`, `krill_stop`, `krill_set_env` (`POST /api/v1/apps/{app}/{deploy|rebuild|reload|stop|env}`). **There are no destructive operations at all** — nothing creates or deletes an org/project/environment/app/DB/domain/volume, and there is no `docker exec`/terminal; the blast radius is bounded by the surface, not by a permission matrix (a list of twelve is checkable by eye). `{app}` is a numeric id or a `project/environment/app` path (`api.Service.resolveApp`; cross-org ⇒ **404, never 403**).

**Auth:** org-scoped bearer tokens in `api_tokens` (**migration 000040**) — `krill_pat_<32B base64url>`, stored as SHA-256 + an 8-char lookup prefix (index NOT unique; candidates are compared constant-time), plaintext shown **once** via the `krill_flash_token` one-shot cookie and unrecoverable. `Identity.CanWrite()` = token `level` ∩ the owner's **live** role (`>= RoleAdmin`), re-resolved by `Authenticator.Authenticate` on every request — demoting or removing the member kills their write token instantly, with no revocation step. `RequireAPIToken` (`internal/server/api_middleware.go`) accepts the token **only** from `Authorization: Bearer` (never `?token=` — query strings land in proxy logs/history), rate-limits **60 req/min per token** (429 + `Retry-After`), and stashes the Identity via `api.WithIdentity` — which is why the identity ctx key lives in `internal/api` (`internal/mcpsrv` must not import `internal/server`; that would cycle). Both surfaces are registered BEFORE the `RequireAuth` group and exempted from `csrfGuard` (an MCP client sends no `Origin`); the ONE `mcpsrv` handler instance is mounted at both `/mcp` and `/mcp/*` (it owns the `Mcp-Session-Id` session table — two instances would lose sessions).

**An MCP tool must NOT read the Identity from its handler's `ctx` (2026-09-23):** in a stateful go-sdk session every handler runs on the context of the request that opened the session (`initialize`), so `ctx` kept the first request's identity (and request id) for the session's whole life — a demotion never reached an open session, and another valid token presented with a leaked `Mcp-Session-Id` ran as the session's owner. `mcpsrv.Handler` now lifts each request's Identity into an SDK `auth.TokenInfo` (`bindSession`, via `auth.RequireBearerToken` — the SDK's context key is unexported, and it verifies nothing new), tools read it from `req.Extra.TokenInfo` (`callerIdentity`), and `TokenInfo.UserID = "token:<id>"` binds the session to the token that opened it, so the SDK refuses any other token with 403 "session user mismatch" (`TestMCPSessionSeesDemotion`/`TestMCPSessionRejectsAnotherToken` in `internal/server`). REST has no sessions, so it never had this. **`KRILL_AGENT_API_ENABLED` (default true) gates BOTH surfaces** — false leaves the authenticator unwired and `/api/v1` 404s too. (It was `KRILL_MCP_ENABLED` until 2026-08-13; renamed because it never gated MCP alone.) Deploys are **async** (`{deployment_id, status}` → poll `krill_deployment_status`); logs are bounded (runtime tail default 200 / max 1000, build-log tail ~8 KB); **`krill_list_env` returns names + source (`literal`/`db-link`) and NEVER values** (everything an agent reads reaches its model provider); `krill_set_env` edits a single `env_text` line (order/comments preserved, duplicate key ⇒ conflict) and does **not** redeploy. Errors are `api.Error{Code,Message}` → HTTP status (REST) / `isError` text (MCP); internal errors never leak `err.Error()` (generic text + `request_id`). Every write logs an INFO audit line with `token_id`/`user_id` (never the token, never an env value); at startup a non-`https` public URL with the API enabled logs a warn. UI: Settings → **API tokens** (`/orgs/{id}/api-tokens`; create is admin-gated, list/revoke only need membership and only ever touch the caller's own tokens).

**Provisioning (2026-11-21):** four creating operations — `krill_create_database` / `POST /api/v1/environments/{project}/{env}/databases`, `krill_create_app` / `…/apps`, `krill_add_domain` / `POST /api/v1/apps/{app}/domains`, `krill_link_database` / `…/db-links` — for a third token level `provision` (migration 000063 widens `api_tokens_level_check`; `Identity.CanProvision` = provision ∩ live admin; `CanWrite` accepts provision too; the previous release treats a provision token as read-only, never stronger). Still nothing deletes or changes an existing resource. `api.Service` owns the gate (`requireProvision` BEFORE resolving anything, like `requireWrite`) and tenancy (`resolveEnv` by project/environment NAMES, 404 outside the org); the work is `server.apiProvisioner` (wired in `SetAPI`), which reuses the UI's building blocks — `hostshare.CreateApplication/Add/UpdatePaths/SetTLS`, `dbservice.ProvisionLogicalDB` with the row-rollback, `syncAppLabelsCtx`, `linkVarTakenCtx` (ctx variants of the UI helpers) — so an API-created resource matches a UI-created one. Idempotency is by natural key (env+name, app+host, app+var): identical repeat → existing with `created:false` (a domain repeat also re-syncs labels, recovering a failed first sync); different settings → `409`. Create-app is image-only and never deploys; its primary domain defaults to `<name>.<base domain>`, internal. MCP argument structs embed the `api.*Input` REST bodies; `TestProvisionToolSchemasAreFlat` pins that the SDK flattens them. Review hardening (same date): each operation holds an `oplock` on its natural key (`api-provision:<kind>:<scope>:<name>`) from lookup to write, and a db-link to a logical database also waits on that database's key, so concurrent identical requests and a link racing a still-provisioning database are both safe (one process); the database is provisioned and rolled back on a context detached from the request (`provisionTimeout`); create-app writes the app, primary-domain settings and registry in ONE transaction under the host reservation (`hostshare.CreateApplicationConfigured`); the app repeat check includes the tag; `DomainInput.TLS` is `*bool` — on a shared host an omitted value inherits, an explicit different one is 409; a name-or-id reference matching one resource by name and another by id, and an environment path two projects share, are refused as ambiguous; `domains`/`db-links` are peeled off as verbs only on POST (`postOnlyVerbs`), so apps with those names keep their GET status route. **`dbservice.ProvisionLogicalDB` now checks `pg_database`/`pg_roles` first and returns `ErrObjectsExist` without touching anything** — before, a collision with a database Krill did not create (restored by hand from a dump) failed CREATE and the compensating `DROP DATABASE … WITH (FORCE)` deleted it (UI and API alike); psql runs with `-X`. `syncAppLabelsCtx` skips the Swarm write when the labels already match (an unchanged ServiceUpdate resets UpdateStatus, which a converging deploy reads as done). The 000063 down migration maps provision tokens to `read`, not `write`. `KRILL_MCP_SESSION_TIMEOUT` (default `30m`, `0` disables) closes an idle MCP session and frees its goroutine: a session ends explicitly only on `DELETE /mcp`, which a crashed agent or a finished CI job never sends. Agent-side runbooks live in [`skills/krill-deploy/SKILL.md`](../../skills/krill-deploy/SKILL.md). Live acceptance (no MCP client has connected yet) is queued in ROADMAP. See `docs/superpowers/specs/2026-08-13-krill-mcp-agent-api-design.md` / `docs/superpowers/plans/2026-08-13-krill-mcp-agent-api.md`.

**Diagnostics (2026-11-26):** four more operations and new parameters, because agents kept falling back to ssh for what the API did not show (task state and health, logs over a window with grep, waiting for a log line, settings and the `backups` table via `psql`, DNS and certificates via `dig`/`openssl`) and polled deployments every few seconds. Read: `krill_app_config` / `GET /api/v1/apps/{app}/config`, `krill_list_backups` / `GET /api/v1/backups?app=|environment=`, `krill_domain_status` / `GET /api/v1/apps/{app}/domain-status`; write: `krill_backup_now` / `POST /api/v1/backups/{kind}/{id}/run`. Twenty operations in all (sixteen plus the four provisioning ones). Each optional dependency the service cannot import is wired in `Server.SetAPI` like the `Provisioner`: `SetInstanceURL(s.baseURL)`, `SetStopping(s.streams())`, `SetMetricsInterval`, `SetResourceDefaults`, `SetBackups(apiBackups)`, `SetGateway(apiGateway)` (`internal/server/api_diagnostics.go`).
- **`krill_whoami.instance`** = `{url, version}`: `Server.baseURL` (`KRILL_PUBLIC_URL`, else the active panel domain, else `KRILL_HOST`), shown as scheme + host + path only (`publicBaseURL`: the public URL may carry a proxy's credentials) and `buildinfo.String()` — app ids repeat across installations, so an agent with several tells them apart by it.
- **`krill_app_status`** adds, all best-effort and `omitempty`: `tasks` (5 newest of `docker.TaskHistory.ServiceTaskHistory`, which also supplies `node` now — one Swarm task read instead of `ServiceTasks`; `TaskRecord` gained `NodeID`/`ContainerID`/`Created`), `failed_since_deploy`/`failed_since` (tasks created since the latest deployment's start that ended `failed`/`rejected`/`complete`; a lower bound, Swarm keeps ~5 tasks per slot), `health` and `usage` from `docker.ContainerProber.ProbeContainer` (one inspect + one `ContainerStatsOneShot` on the task's node through `selectClient`/`RemoteClientProvider`, for every task with desired `running` and a container — a task still `starting` behind its healthcheck included — in parallel under 3 s). **Probe output is never returned** (a probe can echo an env value). `node` is the first task both meant to run and running, by hostname or by node id when the name did not resolve. `usage.cpu_pct` comes from the sampler's `metric_samples` only when it can only be that container's (`attributeCPU`; no other task of the service on the node meant to run or still live — a start-first predecessor with desired shutdown counts — and no worker sharing the sampler key `control-plane`): rows are keyed by node + service and timed at insert, so only a task alone on its node, with a sample more than two sampler intervals after it was created and after every other task of the service there last changed; the samples are read before the task history, so a replacement that produced a sample is in the snapshot. Residual (no container id in `metric_samples` without a migration): a sampler tick delayed by more than that margin could still attribute a predecessor's sample; the sampler names the local node `control-plane` and a worker by `cluster_nodes.name` (matched on `swarm_node_id`). A live CPU% would need two samples (~2 s).
- **`krill_app_logs`** takes `since`/`until` (RFC3339 or a duration ago), `contains` (case-insensitive) and `wait_for` + `timeout` (default 60, max 120 s). **Swarm task logs have no `until`** (the pinned client drops it): `since` goes to Docker (`docker.WindowedLogs.ServiceLogsWindow`, `LogWindow`, `TailAll`; `inWindow` skips tasks that ended before `since` or were created after `until`), the end is applied to the lines in `logWindow.holds`; with `until` the read is from `since` with no tail, otherwise Docker's per-task tail bounds it (`containsScanLines` = 10 000 per task with `contains`). Every window read stays per task and bounded by `logparse.ReadWithin`/`BacklogTimeout` and `maxWindowScanLines` (50 000, `stopReader` ends the stream), kept to the newest `tail` lines, and a cut read ends with the existing incomplete notice. `wait_for` (`waitForLog`, at most `maxLogWaits` = 8 at once across all callers, more → 503) **watches new lines only** (narrowed 2026-11-26 after two review rounds kept finding gaps in the history-then-follow design: memory of a held window, the gap while the follow opens, history/live overlap, cross-task context order). It opens the follow stream (`LogWindow{Follow, Tail: 0, NoDetails}`, no time bound: Docker sends what is written from then on, so a worker whose clock lags the control plane cannot hide a line behind a timestamp cut) and reads until a match (plus up to 10 lines within 1 s), the timeout, the caller going away, the stream ending (`ended`) or breaking (`error`, `incomplete`) or Krill shutting down → `{found, stopped_by, match, lines, following_since, incomplete}`; `following_since` is when the follow call returned (Docker answers before each task's reader is attached and never says when, so the first moments after it may not be covered either; the runbook's closing `contains` read is what covers them). `since` is refused with it (as `contains`, `until`, `level`): earlier lines are an ordinary read's job, and the runbook closes the gap with a `contains` read before the wait and again after a timeout. Memory per wait: the 64-entry live queue and the context ring (exactly `tail` ≤ `maxWaitContext` = 200 entries, a real ring), each line already cut to 16 KB with its timestamp cloned (`keptLine`: a substring would keep the whole raw line, up to 1 MiB, alive), plus the 1 MiB scanner buffer — about 5 MiB at most, 40 MiB for all eight. API reads parse with `logparse.ParseTimestamped` (timestamp only: with `NoDetails` there is no details prefix to strip, and a message starting with `com.docker.swarm.task.id=` keeps it). `inWindow` skips a task only when it is clear of the window by `windowSkew` (1 min): task times are the manager's, log timestamps the worker's. Lines are matched (`contains`, `wait_for`) on the whole message; only the returned copy is cut at 16 KB (`truncMessage`), and the live reader parses, matches and cuts before queueing, so its queue holds small lines. API reads ask for no docker log details (`LogWindow.NoDetails`): Docker prefixes them per frame, so a line joined from two frames could carry a second prefix — a logging driver's env attributes — that the parser does not strip. Without task ids, a `contains` read is reported incomplete once `containsScanLines` lines were scanned (some task may have been capped). `until` still goes to the engine, only to skip tasks created after it. Without `wait_for` the answer is still the array.
- **`krill_deployment_status` `wait`** (`DeploymentStatusWait`, max 120 s, clamped): tenancy first, then `GetDeploymentStatus` (status only — the log can be 256 KB) once a second. `settling` = `Deployer.Settling(id)` (the background settle map): applied, Swarm still converging, still `running`. Polls (every 500 ms) run to the deadline, then the status is read once more and the final row read within `waitReadGrace` (250 ms) past it (`boundedRead`, also ended by the caller and by shutdown); a waiting call is tied to Krill's shutdown from its first lookup on (`withStopping`, both waits); failing the row, the status the wait saw is answered. A failed poll is retried; a deployment that disappears (its app deleted) is `not_found`. **Both waits end on Krill's shutdown**, not only on the request: an MCP tool runs on the session's context, which neither a shutdown nor a disconnected POST cancels, so the service watches the `StopStreams` context (`waitContext`) and MCP passes the carrying request's `Done` through `TokenInfo.Extra` (`extraRequestDone`, `requestScoped`). One waiting call is one request of the 60/min budget.
- **`krill_app_config`** (`api.AppConfig`): source (git URL as scheme + host + path only, an scp-style address as host:path, nothing at all when unparseable — `displayRepoURL`: userinfo, query and fragment can each carry a token; branch/Dockerfile as the builder resolves them; build args and secrets by name only), resources (limits with their source, explicit / instance default / none — an instance default the deployer cannot parse counts as none, and an app's own value that parses to zero falls back to the default, both as the deploy does; Krill has no reservations), placement (worker names), healthcheck timing **without the command**, ports, volumes, domains with protection kinds (never users/hashes/lists), links, and `pending` from `Deployer.PendingChanges` (the "Apply settings" comparison; `known:false` without a recorded fingerprint or with a deploy in flight). Never env values, the command or predeploy command, webhook secret, metrics token or credentials.
- **Backups:** `ListOrgDatabaseBackups`/`ListOrgVolumeBackups`/`ListOrgBucketBackups` + `ListLatestOkBackupRuns` (no migration). `running` comes from the services' new `Running(id)` over their `inFlight` maps; `last_success_at` is the row's own `last_run_at` when the last run succeeded (stable while the notifier journals that run), else the latest `ok` row of `backup_runs` (30 days); `last_error` is `backupErrorSummary`: a Krill-written category (credentials refused, destination unreachable, ran out of time, …), never the stored text — a regex mask was not enough (SDK errors echo access-key ids, quoted values, bearer tokens). `running` is sampled before the rows are read (`ListOrgBackupIDs`) and after, so a run that ends during the read still reads running instead of pairing `running:false` with the previous result. `last_run_at` and `started_at` are rendered to the microsecond (`formatMicro`), PostgreSQL's precision: the run's result is the entry whose `last_run_at` **equals** its `started_at`. `BackupNow`: `requireWrite` before any lookup, chain to the org (404), `apiBackups.Start` → the same `StartBackup`/`StartVolumeBackup` calls and timeouts as "Back up now"; busy → 409; answer carries `started_at` (the exact time `Start` was given, truncated to the microsecond), and the run's result is the entry whose `last_run_at` equals it once `running` is false — a later one is another run's (which overwrote the row) and leaves this run's outcome unknown. A manual run applies the configured retention like a scheduled one. Known gap (pre-existing): a successful upload whose retention pass exhausts the run deadline writes its `ok` on the expired context, so the run reads as having recorded nothing. On the way: a database or volume backup whose run deadline expired could not record its failure (the write used the expired context, leaving the previous `ok`); `fail` now writes on `context.WithoutCancel` bounded by `resultWriteTimeout` (10 s) and logs a failed write, in all three services (bucket backups had the detached write without the bound), so a stalled database cannot hold the run's claim.
- **`krill_domain_status`** (`internal/api/domains.go`): for each stored host of the app, `net.DefaultResolver` (3 s), `points_at_gateway` against `apiGateway.Addresses` (`apiGateway.Locate`, its own 3 s inside the budget so a slow Swarm leaves the DNS and TLS checks time, and inside it the advertised host's resolution and the placement lookup side by side: resolved `KRILL_ADVERTISE_ADDR` + the Swarm addresses of the nodes running a `krill-traefik` task — host-mode ports answer only there, not on every manager; absent when unknown, `gateway_known` false). The handshake goes to the node the gateway task runs on when known, else `KRILL_ADVERTISE_ADDR`, else loopback. DNS lookup errors are Krill's wording too (`lookupError`: the resolver's address stays out). **The addresses are never listed, and a failed handshake's error is Krill's own wording, without the dialed host or address or a resolver's** (`handshakeError`): node addresses are operator data (`RequireInstanceAdmin` territory), not an organization's, and for every `tls` domain — a non-exposed one too, it can carry an HTTPS redirect router — a handshake with `apiGateway.DialAddr()` (`KRILL_ADVERTISE_ADDR`, else `127.0.0.1`):443 with SNI = host, `InsecureSkipVerify` to see what is served, then `x509.Verify` against the system roots: issuer, validity, `days_left`, `trusted`, `default_cert` (`TRAEFIK DEFAULT CERT`). The only connection ever made goes to the configured gateway address, never to an address from DNS, so `netguard` is not involved. 4 in parallel, 15 s overall.
- **Routes:** `config` and `domain-status` are `refShapedVerbs`: peeled off only after a well-formed reference (a numeric id or three segments), so an existing app named `config` keeps `GET …/proj/env/config`. See `docs/superpowers/specs/2026-11-26-agent-api-harness-gaps.md` (local).
