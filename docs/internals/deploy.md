# Deploys and builds

The deploy pipeline, its invariants, app settings that feed the Swarm spec, private images and git, auto-deploy, and app volumes.

## Deploy invariants

### Deploy waits for convergence before marking done — baseline-relative

Before `ServiceDeploy` the deployer snapshots the service's task IDs (`engine.ServiceProgress(name, nil)`), then polls `ServiceProgress(name, baseline)` until `Running >= Desired` counting ONLY tasks outside the baseline (`KRILL_CONVERGE_TIMEOUT`, 1s interval). Counting all tasks (old `ServiceState` behavior) would declare every redeploy converged instantly on the old StartFirst task. A `rollback_*` `UpdateState` fails the deploy ("update rolled back").

### A deploy is done only when Swarm is

*(2026-11-21)*

A service still starting after `KRILL_CONVERGE_TIMEOUT` used to be recorded `done` (app `deploying`, log "continuing in the background") while the new image was still pulling and the old version served — a live deploy said done 2 minutes before Swarm completed. Now `run` hands any not-yet-converged, not-failed service (`Found && (Desired > 0 || Global)` — `ServiceProgress.Global` because a global service's Desired is its count of new tasks, 0 while no eligible node is up; including a FIRST deploy still pulling, where Swarm reports no update status and Running=0, which used to be recorded `error`, and a rollback, which used to give up) to `Deployer.startSettle`: a goroutine (in `d.wg`, under `d.runCtx`, so `Stop` cancels and waits for it) that polls `ServiceProgress` every `settlePollInterval` for up to `settleTimeout` (20m) and records the real outcome — done via the same `complete` closure (release confirmation, `DeploySucceeded`), error on rollback / crash loop, or error `timed out waiting for the service to converge`. The build worker is free meanwhile, but the deployment row stays `running`, so the per-app in-flight check refuses another deploy of that app and it counts toward `KRILL_MAX_BUILDS_PER_ORG` and the self-update busy check. The placement oplock is NOT held during the settle. The watch ends early when the service is stopped/removed (`!Found || (Desired == 0 && !Global)` → deployment `error` "stopped before the service converged", app status left to the stop, no alert) and when another deploy of the app starts — only `EnqueueSystem` (the org-network migrator) can, since it bypasses the per-app check — via `supersedeSettle`, called just before that deploy's `ServiceDeploy` (not earlier: a system deploy failing while it prepares must leave the earlier rollout's watch alone) (`settling` map, `context.WithCancelCause(errSuperseded)`), so the old watch never confirms the newer spec. Known gap: `ServiceProgress` counts only desired-running tasks, so a replica slot that keeps crashing (each failed task gets desired=shutdown) is not seen as a crash loop and ends as a timeout. A shutdown (`stopping()`) records the deployment `error` "interrupted: krill stopped before the service converged" and leaves the app `deploying` (`finishInterrupted`; it used to be `done`). **Nothing used to rewrite such a `deploying` (2026-11-25, v0.13.4):** the comments promised a "live status poll" that never wrote the column, so an app interrupted this way — or by a crash, a shutdown with the job still queued, or v0.9.4's old "done, still starting" path (base13 on msk since deploy 36) — stayed `deploying` forever. `deploy.StartStatusHeal` (at startup after `FailOrphanedDeployments`, then once a minute) lists apps `deploying` with no `running` deployment (`ListStuckDeployingApplications`) and sets idle/running from the live service, or error once `settleTimeout` has passed since the last deployment ended with the service still short; the write is conditional (`HealApplicationStatus`), so a deploy started in between keeps its status. No notification. A job whose own `jobTimeout` expired mid-wait also goes to the settle, not to the shutdown branch.

### Stop cancels an unfinished deploy

*(2026-11-24, v0.13.2)*

A Stop used to scale a service the queued or still-preparing deploy had not created or updated yet (a silent no-op), say "stopped", and the deploy then brought the app up (seen on v0.13.1 by the self-update acceptance run). Now both Stops (`stopApp`, `api.Service.Stop`) go through `Deployer.StopApp(ctx, appID, by, scale)` (`internal/deploy/stop.go`). Every accepted deploy is tracked by deployment id from `submit` until its outcome is written (`tracked`, phases queued → preparing → applying). Under `admitMu` (so no deploy of the app is between its row and its tracking) StopApp marks each queued/preparing deploy cancelled, cancels a preparing one's job context (`docker build` and predeploy are killed through it — a running predeploy command such as a migration is interrupted), and takes cancelled jobs out of the queue (`compactQueue`: a cancelled job used to keep its slot while its in-flight caps were free, so deploy+stop in a loop during a long build could fill the shared queue). The queue is a `jobQueue` (`internal/deploy/queue.go`, FIFO under a mutex, capacity `queueCapacity`) rather than a channel for exactly this: filtering a channel means emptying it, and meanwhile the worker could run a later job first or the shutdown drain could miss the jobs held aside. StopApp waits for `admitMu` only as long as its context allows (`lockAdmit`), and waits for a cancelled run to wind down (`exited`: its build killed, its predeploy container removed) before scaling. It writes each as `error` "stopped by <email> before it was applied" (deploy log too, no `DeployFailed` alert), so the per-app and per-org slots and the self-update busy check are free when it returns; a failed write is returned as an error and retried by the next Stop (`persisted`/`workerDone` keep the record until both hold; `persisting` makes two simultaneous Stops write it once). Deploy logs are made storable before any write (`storable` in `logs.go`: the byte caps can cut a multi-byte character, a command can print a NUL, and PostgreSQL then refuses the whole update, status included). It waits for a deploy writing its outcome at that moment (`finishing`/`done`), then calls `scale` under `oplock.AppRouting` — the lock the deployer holds from its last check (`enterApply`, the point of no return right before `ServiceDeploy`) to the end of `ServiceDeploy`. So exactly one wins: either the stop marked the deploy first and `enterApply` refuses it, or the deploy passed and the stop scales the spec it just wrote. Only after `scale` succeeded is an applied deploy marked `stoppedBy` (one that began recording its outcome meanwhile is waited for instead): it then ends within a poll once it sees the service at zero ("stopped by … before the service converged"; it used to wait out `KRILL_CONVERGE_TIMEOUT` and alert "service did not converge"), and what it records leaves the app status to the stop and sends no notification; a failed stop leaves it reporting normally. Paths that record an outcome on their own (`failQueued` at shutdown, a send refused at shutdown) claim it atomically (`claimFinish`). Queued, preparing, Dockerfile, rollback and `EnqueueSystem` deploys all take this path; a system deploy (the network migration) that finds its app's service at zero or gone (a stopped global service is removed) under the routing lock is skipped ("skipped: the application was stopped", no alert) instead of starting it. A tag carried by a cancelled image deploy stays the app's tag (it is written on acceptance). Not covered: other ways to take a service down mid-deploy (app delete, a volume restore's quiesce), and a `ServiceCreate` whose job deadline expires after the daemon accepted it. The acceptance harness's `endBusyDeploy` still waits for the applied spec before pressing Stop, on purpose.

### Deploy jobs carry their tag

*(2026-09-22)*

The worker reads the application row when it picks a job up, not when it was queued, so an image app's new image/tag must travel in the job: `Deployer.EnqueueImage(appID, trigger, image, tag)` puts them in `job`, the store applies them (`GetDeploymentApp(ctx, id, ImageRef)`) BEFORE the registry-credential host check so the credential is checked against the image actually pulled, and the application row is written (`SetApplicationImage`) only after the job was accepted into the queue. Never retag `applications` before enqueueing: a refused deploy would leave the tag behind, and a deploy already in flight could ship it.

### Deploy refusals are typed

*(2026-11-06)*

`Deployer.enqueue` returns `(id, error)`: `ErrDeployInFlight`, `ErrOrgDeployLimit`, `ErrQueueFull`, `ErrDeployerStopped`, or a wrapped store error; the `Enqueue*Err` methods expose it (the `int64` ones remain for callers that only need the id). A full queue is refused under `admitMu` BEFORE a deployment row exists — it used to record a failed deployment and mark a possibly healthy app `error`. UI flashes say which refusal (`deployRefusalKey`); the API maps in-flight to `409 conflict` and the rest to `503 unavailable` + `Retry-After` (`api.refusal`).

### `ServiceSpec.LogDriver` is `json:",omitempty"` on purpose

The observability agents and the gateway hash the whole serialized `ServiceSpec`, so a new field that serializes when unset changes every fingerprint and redeploys those services on upgrade. Give any new optional `ServiceSpec` field the same tag. The gateway sets json-file 5×20m so its access log can't fill the disk.

### Build logs are bounded

**Build logs are bounded** — head (128 KB) + tail (128 KB) buffer with a `...[truncated N bytes]...` marker only when the middle is actually dropped (`internal/deploy/logs.go`).

## App lifecycle controls

Deploy/Reload/Rebuild/Stop buttons on the app General tab. Reload = `engine.ServiceRestart` (no rebuild) for a running app, but a full deploy for a stopped (0 replicas) or never-deployed one — a restart would bring it back on the spec it was stopped with, i.e. the shared network after the org-network migration (the API's `Reload` then returns `{action:"deploy", deployment_id}`); Rebuild = `EnqueueRebuild` (`docker build --no-cache`); Stop = `Deployer.StopApp` (cancel every deploy of the app that has not applied its spec, then `ServiceScale → 0` — see [Stop cancels an unfinished deploy](#stop-cancels-an-unfinished-deploy)), the same for the UI and the API's `krill_stop`; Deploy brings it back up.

## Advanced container settings

nullable `applications` columns `memory_limit`/`cpu_limit`/`replicas`/`restart_condition`/`restart_max_attempts`/`healthcheck_*`; human units (`256m`/`0.5`/`30s`) parsed by `docker.ParseMemoryBytes`/`ParseNanoCPUs` → `ServiceSpec` `Resources.Limits` + `RestartPolicy` + `Healthcheck` in `buildSwarmSpec`; carried from the store into the deploy spec. UI: app "Advanced" tab (no reservations/placement/raw-JSON yet).

## Resource defaults & build caps

apps and DB instances with no explicit memory/CPU limit of their own now fall back to an instance-wide default — `KRILL_DEFAULT_MEMORY_LIMIT`/`KRILL_DEFAULT_CPU_LIMIT`, applied in `Deployer.withResourceDefaults` and `dbservice.Service.instanceSpec` only where the app/instance's own value is `0`, so an explicit per-resource value always wins and an unlimited container can no longer take the whole host by default. `KRILL_MAX_BUILDS_PER_ORG` caps how many deploys one organization may have in flight on the shared single-worker build queue at once, on top of the pre-existing per-app "one deploy in flight" check (`CountRunningDeploymentsByOrg`, checked in `Deployer.enqueue`; `<= 0` disables it, a query error fails closed and refuses the deploy). `internal/builder.StartCachePrune` runs `docker builder prune --force --reserved-space <KRILL_BUILD_CACHE_LIMIT>` on a `KRILL_BUILD_PRUNE_INTERVAL` ticker (Docker CLI 28+ renamed `--keep-storage` to `--reserved-space`; an older CLI that rejects the new flag gets `--keep-storage`, remembered after the first attempt) — nothing else ever trimmed the BuildKit cache, so a small VPS could otherwise fill its disk silently until builds start failing. There is deliberately no per-build network or resource isolation: BuildKit rejects a `--network` override outright and silently ignores `--memory`/`--cpu-quota`, so the queue cap and the cache prune are the only mitigations on the build side; the actual isolation for `krill-postgres` is the installer's `krill-state` network (see [Release, image and installer](operations.md#release-image-and-installer)).

## Registries (private image pull)

org-scoped `registries` table (registry_url/username/password, plaintext) + nullable `applications.registry_id`. `docker.EncodeRegistryAuth(user,pass,url)` → `ServiceSpec.RegistryAuth` → `EncodedRegistryAuth` on `ServiceCreate/Update` (Swarm `--with-registry-auth`); the deployer's store loads+encodes the app's registry. `Engine.RegistryCheck` validates creds on create (engine-gated, so nil-engine tests skip it). UI: org Registries page (admin) + a registry select on app create/General. Real private pull verified on a host.

## Credential host binding

Git and registry credentials are checked against the host they were created for before Krill will use them. `internal/builder.HostOf`/`NormalizeHost` and `internal/docker.RegistryHost`/`ImageHost` normalize the credential's stored host and the app's `git_url`/`image` host for comparison; `internal/deploy/store.go`'s `checkGitCredentialHost`/`checkRegistryHost` run inside `GetApplication`, before the deployer ever reaches a clone or a pull, and fail closed — including when the stored host itself normalizes to empty, which used to bypass the check entirely. `createGitCredential`/`createRegistry` also refuse to store a credential whose own host doesn't normalize to something usable, closing the same gap at the source. A Dockerfile app's `git_url` additionally goes through the existing SSRF egress guard (`internal/netguard.CheckHost`, gated by `KRILL_ALLOW_PRIVATE_EGRESS`) before the clone starts — the same treatment S3 and registry URLs already had.

## Build secrets/args + private git

org-scoped `git_credentials` (PAT, token `secret.Enc`; migration 000021) + nullable `applications.git_credential_id`; private HTTPS clone authenticates via a `GIT_ASKPASS` helper (`builder.gitAuthSetup`) — the token is fed to git through env vars, never embedded in the clone URL/argv or written to the member-visible build log (`sanitizeGitURL` also strips any credentials before echoing). `applications.build_args` (non-secret → `--build-arg`) + `build_secrets` (`secret.Enc` → BuildKit `--secret` via `0600` temp files outside the build context, `DOCKER_BUILDKIT=1`, defer cleanup). Dockerfile source only. UI: org "Git credentials" page + per-app select + build_args/secrets editors on the Advanced tab (secrets masked, plaintext admin-only). Deferred: SSH deploy-keys.

## GitHub auto-deploy

*(Phase 6)*

per-app, opt-in (`applications.auto_deploy`, default false; migration 000026), **webhook + PAT** (no OAuth/GitHub App). One per-app secret (`webhook_secret`, `secret.Enc`) serves both mechanisms; kept across disable→enable. Two PUBLIC endpoints registered before the `RequireAuth` group (auth is the secret, not a cookie; `csrfGuard` exempts the `/webhooks/` prefix): **Dockerfile/git apps** → `POST /webhooks/github/{appID}` verifies HMAC `X-Hub-Signature-256` (`webhook.VerifyHMAC`, constant-time), matches `ref` to `git_branch`, then `deployer.Enqueue(appID,"webhook")` → build+deploy (`ping`/unknown event/non-matching branch → 200 no-op; **bad sig → 404**, same as unknown/disabled/wrong source_type → so the endpoint never leaks which app IDs have auto-deploy enabled). **Image apps** → `POST /webhooks/deploy/{appID}` checks the secret from the `Authorization: Bearer` header only — `?token=` is not read (constant-time, empty stored secret rejected explicitly; bad token → 404); when the deploy cannot be queued (a deploy of that app is already in flight, or the organization is at `KRILL_MAX_BUILDS_PER_ORG`) both webhook endpoints answer **503 with `Retry-After`** instead of a silent 202, optional `?tag=` (`webhook.ValidTag` → `UpdateApplicationImage`), then re-pull+deploy; the CI calls it after `docker push`. Both endpoints answer **503 + `Retry-After: 30`** when the deployer refuses the deploy (already in flight for the app, the per-org `KRILL_MAX_BUILDS_PER_ORG` cap, a full queue) instead of acknowledging a deploy that never happened; A `?tag=` travels with the deploy job (`Deployer.EnqueueImage`, see [Deploy jobs carry their tag](#deploy-jobs-carry-their-tag)), so a refused deploy never touches the app's tag. The pure helper package is `internal/webhook` (`VerifyHMAC`/`ParsePushEvent`/`NewSecret`/`ConstantTimeEqual`/`ValidTag`, no GitHub SDK). Admin handlers `enableAutoDeploy`/`disableAutoDeploy`/`regenerateWebhookSecret` (admin-gated, tenant-chain) + a General-tab Auto-Deploy section (URL + masked secret reveal/copy + Regenerate, admin-only; webhook URL built from `Config.BaseURL()` ← `KRILL_PUBLIC_URL` or `KRILL_HOST`+scheme).

**Same-tag re-pull fix:** `Engine.ResolveDigest` (registry `DistributionInspect`, no pull) pins image apps to `repo@sha256:…` in the deployer so a redeploy of an unchanged tag (`:latest`) actually pulls the new image (best-effort: `slog.Warn` + plain-tag fallback on error). Deferred: OAuth/GitHub App, repo/branch picker, auto-creating the webhook in GitHub, native GHCR `registry_package`, coalescing rapid pushes. See `docs/superpowers/specs/2026-06-20-krill-phase6-github-autodeploy-design.md`.

## App volumes/mounts + backup/restore

`app_volumes` table (migration 000018) + a Volumes tab (admin); the deployer carries `Mounts` into `buildSpec` (fixes drift mount-loss on redeploy) and volumes are cleaned up on app/env/project delete. `docker.VolumeArchive`/`VolumeRestore` run a pinned-digest busybox sidecar (root, no network, ro archive) to tar a named volume → `volume_backups` + `internal/volume.VolumeService` (backup→gzip→S3 with count retention; restore quiesces the app first). A second `backup.Scheduler` drives cron; handlers are admin-gated with IDOR + cross-org destination checks. The live archive/restore path is verified on a real host (backup+restore round-trip of prod Readeck → MinIO).

## Pitfalls

### Changing `UpdateConfig.Order` itself takes effect in the very rollout that changes it, not the next one

**Changing `UpdateConfig.Order` itself takes effect in the very rollout that changes it, not the next one** — verified empirically (`internal/docker.TestUpdateOrderChangeAppliesInSameRollout`, `-tags=integration`): a service redeployed from a start-first spec to a stop-first spec in one `ServiceDeploy` call stops the old task before starting the new one for THAT deploy, not just for deploys after it. Nothing in the docker/swarm client API documents this either way, so it isn't safe to assume — this is what makes "an existing DB instance protects itself at its next deploy" (see [Stateful services](databases.md#stateful-services--engine-drivers)) true without an extra scale-to-zero step.

### A volume restore REPLACES the volume's contents

*(2026-08-05)*

`VolumeRestore` clears the mount point (dotfiles included) before extracting, because `tar -x` alone only overwrites paths present in the archive — anything created after the backup used to survive, silently merging two points in time. Callers already quiesce the app first. Verified on real Docker by `TestVolumeRestoreReplacesExistingContent` (`-tags=integration`).
